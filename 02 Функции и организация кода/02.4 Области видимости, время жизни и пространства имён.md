# 02.4 Области видимости, время жизни и пространства имён

> [!abstract] О чём урок
> - **область видимости**: где имя доступно;
> - **время жизни**: когда объект создаётся и уничтожается; автоматическое и статическое;
> - глобальные переменные и почему движки обращаются с ними осторожно;
> - `static` внутри функции;
> - **пространства имён**: своё `ember`, вложенные пространства, `using`;
> - псевдонимы типов.
>
> Область видимости и время жизни — разные вещи, и их путают. Первое — про **имена** (компилятор), второе — про **объекты** (работающая программа).

## Область видимости

**Область видимости** (scope) — часть кода, где имя можно использовать.

```cpp
int main() {
    int score = 0;                 // видна до конца main

    for (int wave = 1; wave <= 3; ++wave) {   // wave видна только внутри for
        int enemies = wave * 5;    // видна только внутри тела цикла
        score += enemies;
    }
    // здесь wave и enemies уже не существуют

    if (int bonus = score / 10; bonus > 0) {  // bonus видна в if и else
        score += bonus;
    }
}
```

Правило: имя видно от точки объявления **до конца блока** `{ }`, в котором оно объявлено. Переменные цикла `for` и `if` с инициализатором видны внутри соответствующей конструкции.

> [!tip] Объявляй переменные как можно позже
> Объявляй переменную прямо перед первым использованием и в самом узком блоке. Так меньше шансов случайно использовать её не там, а читателю не нужно держать в голове лишние имена. В старом C все переменные полагалось объявлять в начале функции; в C++ так делать не нужно.

### Затенение

Имя во внутреннем блоке может **затенить** (shadow) такое же имя снаружи:

```cpp
int health = 100;
if (isPoisoned) {
    int health = 50;          // НОВАЯ переменная, затеняет внешнюю
    health -= 10;             // меняется внутренняя
}
// внешняя health по-прежнему 100
```

Обычно это ошибка: программист хотел изменить внешнюю переменную, а случайно написал `int`. С `/W4` MSVC предупреждает: `C4456: объявление "health" скрывает предыдущее локальное объявление`.

## Время жизни

**Время жизни** (lifetime, storage duration) — промежуток работы программы, когда объект существует в памяти. Главные виды:

| Вид | Кто | Создаётся | Уничтожается | Где в памяти |
|---|---|---|---|---|
| **Автоматическое** | Локальные переменные и параметры | При входе в блок / объявлении | При выходе из блока | Стек |
| **Статическое** | Глобальные переменные, `static`-переменные | До `main` (или при первом проходе для `static` в функции) | После выхода из `main` | Сегмент данных программы |
| **Динамическое** | То, что создано через `new` или контейнерами | Когда попросили | Когда освободили | Куча (модуль 03) |
| **Потоковое** | `thread_local` | При старте потока | При завершении потока | Своя у каждого потока (модуль 14) |

С автоматическим временем жизни мы уже хорошо знакомы по [[02.2 Как работает вызов — стек и рекурсия#Время жизни локальных переменных|уроку 02.2]]: переменные живут ровно до конца своего блока.

> [!deep] Под капотом: деструкторы и конец блока
> «Уничтожается при выходе из блока» — это не просто «память больше не используется». Для объектов вроде `std::string` и `std::vector` при выходе из блока **автоматически вызывается код**, который освобождает их буфер в куче (**деструктор**). Строка `}` в конце блока на самом деле может выполнить много работы. На этом механизме держится вся система управления ресурсами в C++ (RAII), и это главная тема модуля 04.

## Глобальные переменные

Переменная, объявленная **вне функций**, — глобальная: видна во всём файле (после объявления) и живёт всё время работы программы.

```cpp
int frameCounter = 0;          // глобальная переменная

void update() {
    ++frameCounter;
}
```

Глобальные переменные **инициализируются нулём** (в отличие от локальных!), если значение не задано.

> [!warning] Почему глобальных переменных избегают
> - **Скрытые зависимости.** По подписи `void update()` не видно, что она меняет `frameCounter`. Чтобы понять, кто и когда меняет глобальную переменную, нужно прочитать весь код.
> - **Тестирование.** Функцию, которая зависит от глобального состояния, трудно проверить отдельно: нужно воспроизвести всё окружение.
> - **Многопоточность.** Глобальная переменная доступна всем потокам сразу, и одновременная запись приводит к гонкам (модуль 14).
> - **Порядок инициализации** (см. ниже).
>
> Это не значит «никогда». Константы (`constexpr`) в глобальной области — совершенно нормально. А изменяемое глобальное состояние должно быть исключением, а не привычкой.

> [!deep] Фиаско порядка статической инициализации
> Глобальные объекты инициализируются до `main`. Внутри одного `.cpp` — сверху вниз. А вот **между разными `.cpp` порядок не определён**. Если глобальный объект в `renderer.cpp` при инициализации использует глобальный объект из `log.cpp`, а тот ещё не инициализирован, программа обращается к неготовому объекту. Это называется **static initialization order fiasco**: баг, который зависит от порядка, в котором линковщик сложил объектные файлы, и может появиться после переименования файла.
>
> **Как это решают движки:** не создают сложных глобальных объектов «самих по себе», а явно инициализируют подсистемы в функции запуска в известном порядке: `log::init(); memory::init(); renderer::init(); ...` и выключают их в обратном порядке. Так сделаем и мы в Ember.

## `static` внутри функции

Локальная переменная с `static` имеет **статическое** время жизни: она создаётся **один раз** (при первом проходе через объявление) и сохраняет значение между вызовами. При этом её **видимость** остаётся локальной: снаружи функции к ней не обратиться.

```cpp
#include <print>

int nextEntityId() {
    static int counter = 0;     // инициализируется один раз
    return ++counter;
}

int main() {
    std::println("{}", nextEntityId());   // 1
    std::println("{}", nextEntityId());   // 2
    std::println("{}", nextEntityId());   // 3
}
```

Вот наглядный пример того, что область видимости и время жизни независимы: видна `counter` только внутри функции, а живёт всю программу.

> [!deep] Инициализация `static` потокобезопасна
> Начиная с C++11, инициализация `static`-переменной внутри функции **потокобезопасна**: если две функции из разных потоков одновременно впервые дойдут до объявления, инициализация выполнится ровно один раз, а второй поток подождёт. Компилятор генерирует для этого скрытый флаг и проверку («magic statics»). Проверка стоит немного, но в очень горячем коде её иногда учитывают.

## Пространства имён

Помнишь, как `log` из библиотеки C помешал нам назвать так свою функцию ([[02.1 Функции#Перегрузка|урок 02.1]])? Чем больше проект, тем больше вероятность конфликта имён: функция `init` есть у рендера, звука и физики, класс `Vector` — в каждой второй библиотеке. Решение — **пространства имён** (namespaces):

```cpp
#include <cmath>
#include <print>

namespace ember {

constexpr float pi = 3.14159265f;

float degreesToRadians(float degrees) {
    return degrees * pi / 180.0f;
}

}   // namespace ember

namespace ember::math {    // вложенное пространство имён (C++17)

struct Vec2 {
    float x = 0.0f;
    float y = 0.0f;
};

float length(Vec2 v) {
    return std::sqrt(v.x * v.x + v.y * v.y);
}

}   // namespace ember::math

int main() {
    float rad = ember::degreesToRadians(90.0f);
    ember::math::Vec2 velocity{3.0f, 4.0f};
    std::println("{:.4f} {}", rad, ember::math::length(velocity));   // 1.5708 5
}
```

- `namespace имя { ... }` — всё объявленное внутри получает «фамилию»: `ember::degreesToRadians`.
- Пространство имён можно **открывать много раз**, в разных местах и файлах: содержимое складывается.
- `namespace ember::math { }` — короткая запись вложенного `namespace ember { namespace math { } }`.
- Комментарий `// namespace ember` после закрывающей скобки — общепринятая вежливость: в длинном файле иначе непонятно, что закрывает эта `}`.
- Внутри пространства имён к своим именам можно обращаться без префикса: `degreesToRadians` использует `pi`, а не `ember::pi`.

Всё, что объявлено вне любых пространств имён, находится в **глобальном** пространстве. К нему можно обратиться явно через `::`: `::log` — тот самый логарифм из C.

### `using`: как сократить запись

```cpp
// 1. Using-объявление: подтянуть ОДНО имя
using ember::math::Vec2;
Vec2 position{1.0f, 2.0f};

// 2. Псевдоним пространства имён
namespace em = ember::math;
em::Vec2 velocity{};

// 3. Using-директива: подтянуть ВСЁ (с осторожностью!)
using namespace ember::math;
```

> [!warning] Где можно писать `using`
> - **В заголовочных файлах — никогда** (кроме как внутри функций): `using` «протечёт» во все файлы, которые подключат заголовок, и вызовет конфликты у людей, которые о нём даже не знают.
> - **В `.cpp` файлах** — можно, но лучше внутри функции или после всех `#include`, и лучше using-объявления конкретных имён, чем `using namespace`.
> - **`using namespace std;`** — нигде, по причинам из [[01.1 Анатомия программы#Пространство имён std|урока 01.1]].

### Безымянное пространство имён

```cpp
namespace {
    int helperCounter = 0;          // видно только в ЭТОМ .cpp файле
    void internalHelper() { }
}
```

Имена в безымянном пространстве видны только внутри **текущего файла** (единицы трансляции). Другие `.cpp` их не видят, и конфликтов при линковке не будет. Это способ сказать: «это внутренняя деталь реализации файла». Подробнее — в [[02.5 Многофайловые программы и линковщик#Связывание — внутреннее и внешнее|следующем уроке]].

> [!engine] Пространства имён в движках
> - В нашем движке всё будет в пространстве `ember`: `ember::math`, `ember::render`, `ember::platform`.
> - Unreal Engine исторически пространств имён почти не использует. Вместо них у типов **префиксы**: `FVector` (простые структуры), `UObject` (объекты с отражением), `AActor` (акторы), `TArray` (шаблоны), `EState` (перечисления). Это наследие 1990-х, когда поддержка пространств имён в компиляторах была ненадёжной.

## Псевдонимы типов

Длинному или часто используемому типу можно дать короткое имя:

```cpp
using u8  = std::uint8_t;
using u32 = std::uint32_t;
using EnemyList = std::vector<Enemy>;
using Grid = std::array<std::array<bool, 40>, 20>;   // ты уже видел это в «Жизни»
```

`using Имя = Тип;` не создаёт новый тип, а только даёт существующему ещё одно имя. В старом коде то же самое записывали через `typedef`: `typedef std::uint8_t u8;` (порядок обратный и легко путается, поэтому в новом коде пиши `using`).

> [!quiz]- Проверь себя
> 1. Чем область видимости отличается от времени жизни?
> 2. Чем инициализируется глобальная `int` без значения? А локальная?
> 3. Сколько раз выполнится инициализация `static int counter = 0;` внутри функции, вызванной 100 раз?
> 4. Почему нельзя писать `using namespace` в заголовочных файлах?
> 5. Что такое фиаско порядка статической инициализации и как движки его избегают?
> 6. Создаёт ли `using Health = int;` новый тип?
>
> > [!success]- Ответы
> > 1. Область видимости — часть кода, где доступно имя (понятие времени компиляции). Время жизни — промежуток выполнения программы, когда объект существует в памяти.
> > 2. Глобальная — нулём. Локальная — ничем: в ней мусор.
> > 3. Один раз, при первом вызове.
> > 4. Директива распространится на все файлы, которые подключат заголовок, и вызовет у них конфликты имён.
> > 5. Порядок инициализации глобальных объектов из разных `.cpp` не определён, и один может обратиться к другому до его инициализации. Движки инициализируют подсистемы явно, в функции запуска, в заданном порядке.
> > 6. Нет, это лишь псевдоним: `Health` и `int` — один и тот же тип.
