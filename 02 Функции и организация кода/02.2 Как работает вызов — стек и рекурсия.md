# 02.2 Как работает вызов — стек и рекурсия

> [!abstract] О чём урок
> - что такое **стек вызовов** и **кадр стека**;
> - что происходит в процессоре при вызове функции: читаем настоящий ассемблер MSVC;
> - соглашение о вызовах Windows x64: где лежат аргументы;
> - почему локальные переменные «умирают» после выхода из функции;
> - **рекурсия** и **переполнение стека**;
> - **встраивание** (inlining): почему Release-сборка быстрее.
>
> Урок целиком «под капотом». Для прикладного программиста это необязательная теория, а для программиста движков — базовая грамотность.

## Стек вызовов

Когда `main` вызывает `computeDamage`, а та вызывает `clamp`, программа должна помнить:
- куда **вернуться** после завершения каждой функции;
- **локальные переменные** каждой из них, пока она не закончилась.

Для этого у каждого потока программы есть область памяти — **стек вызовов** (call stack). Каждый вызов функции кладёт на стек **кадр** (stack frame), а возврат из функции снимает его. Последний пришёл — первый ушёл, как стопка тарелок.

```
     main вызывает computeDamage, та вызывает clamp:

        ┌──────────────────────┐   ← вершина стека (регистр RSP)
        │ кадр clamp           │
        │  value, lo, hi       │
        │  адрес возврата      │ → в computeDamage
        ├──────────────────────┤
        │ кадр computeDamage   │
        │  baseDamage, armor   │
        │  damage              │
        │  адрес возврата      │ → в main
        ├──────────────────────┤
        │ кадр main            │
        │  playerHealth, ...   │
        └──────────────────────┘   ← дно стека (старшие адреса)
```

Именно это показывала панель **Call Stack** в отладчике ([[00.6 Отладчик — главный инструмент#Пошаговое выполнение|урок 00.6]]): цепочку кадров от текущей функции до `main`. Щелчок по кадру показывал его локальные переменные.

Что лежит в кадре:
- **адрес возврата**: в какое место вызывающей функции вернуться;
- **локальные переменные** функции;
- **сохранённые регистры** процессора, которые функция обязана вернуть в исходном виде;
- место для **аргументов** вызываемых ею функций.

> [!deep] Стек растёт вниз
> На x86/x64 стек растёт в сторону **меньших** адресов: каждый новый кадр располагается ниже предыдущего. Регистр процессора **RSP** (stack pointer) указывает на вершину стека. «Выделить» место под локальные переменные — значит просто **вычесть** число из RSP: одна инструкция, никаких поисков свободной памяти. Поэтому локальные переменные создаются практически бесплатно. Сравни с кучей ([[01.7 Первые составные типы — array, vector, struct#Вектор — динамический массив|вектор]] выделяет буфер в куче), где выделение памяти — вызов сложного алгоритма. Подробно о куче в модуле 03.

## Вызов функции в машинном коде

Возьмём простейшую функцию:

```cpp
int add(int a, int b) {
    int sum = a + b;
    return sum;
}

int main() {
    return add(2, 3);
}
```

Вот что сгенерировал MSVC в **Debug** (`/Od`). Это настоящий листинг, полученный флагом `/FAs`, я только сократил комментарии:

```asm
main PROC
    push  rdi
    sub   rsp, 32               ; выделить 32 байта на стеке («теневое пространство»)
    mov   edx, 3                ; второй аргумент — в регистр EDX
    mov   ecx, 2                ; первый аргумент — в регистр ECX
    call  ?add@@YAHHH@Z         ; вызвать add: положить адрес возврата на стек и прыгнуть
    add   rsp, 32               ; освободить место
    pop   rdi
    ret   0                     ; вернуться; результат add уже лежит в EAX
main ENDP

?add@@YAHHH@Z PROC              ; это и есть add (декорированное имя!)
    mov   DWORD PTR [rsp+16], edx   ; сохранить b из регистра в память
    mov   DWORD PTR [rsp+8], ecx    ; сохранить a из регистра в память
    push  rdi
    sub   rsp, 16                   ; место под локальную sum
    mov   eax, DWORD PTR b$[rsp]    ; загрузить b
    mov   ecx, DWORD PTR a$[rsp]    ; загрузить a
    add   ecx, eax                  ; a + b
    mov   eax, ecx
    mov   DWORD PTR sum$[rsp], eax  ; записать в sum
    mov   eax, DWORD PTR sum$[rsp]  ; прочитать sum в EAX — регистр результата
    add   rsp, 16
    pop   rdi
    ret   0                         ; снять адрес возврата со стека и прыгнуть туда
?add@@YAHHH@Z ENDP
```

Как работает вызов:
1. `main` кладёт аргументы в **регистры** `ECX` и `EDX`.
2. Инструкция `call` кладёт на стек **адрес возврата** (адрес следующей за `call` инструкции) и прыгает на начало `add`.
3. `add` выделяет себе место на стеке, вычисляет и кладёт результат в регистр `EAX`.
4. Инструкция `ret` снимает адрес возврата со стека и прыгает по нему, обратно в `main`.

Обрати внимание, сколько лишних движений в Debug: аргументы из регистров сохраняются в память, потом загружаются обратно, `sum` записывается и тут же читается. Так сделано **специально**: каждая переменная лежит в памяти, и отладчик может её показать и изменить.

А вот **Release** (`/O2`) для той же программы:

```asm
?add@@YAHHH@Z PROC
    lea   eax, DWORD PTR [rcx+rdx]  ; eax = rcx + rdx: вся функция в одной инструкции
    ret   0
?add@@YAHHH@Z ENDP

main PROC
    mov   eax, 5                    ; add(2, 3) вычислено при компиляции!
    ret   0
main ENDP
```

Функция `add` сжалась до одной инструкции. А в `main` её вызова нет **вообще**: компилятор встроил `add` и вычислил `2 + 3` сам. Вот откуда пятнадцатикратная разница в скорости из [[Практикум 00 — Инструменты#Задание 5. Release-сюрприз ⭐⭐|практикума 00]].

> [!deep] Соглашение о вызовах Windows x64
> Как функции договариваются, где лежат аргументы и результат? Этот договор называется **соглашением о вызовах** (calling convention). В Windows x64 оно одно для всех программ:
> - первые **четыре** целых аргумента (и указатели) передаются в регистрах **RCX, RDX, R8, R9**, по порядку;
> - первые четыре дробных — в **XMM0–XMM3**;
> - остальные аргументы — через стек;
> - результат возвращается в **RAX** (целые) или **XMM0** (дробные);
> - вызывающая функция всегда выделяет **32 байта «теневого пространства»** (shadow space) на стеке, куда вызываемая может сохранить свои четыре регистра-аргумента. Это и есть `sub rsp, 32` в `main` и `mov [rsp+8], ecx` в Debug-версии `add`.
>
> Следствие для производительности: функция с **четырьмя и меньше** простыми параметрами получает их в регистрах, это самый быстрый вариант. Структуры размером 1, 2, 4 или 8 байт тоже передаются в регистре, а всё крупнее — через память, по указателю на копию. Поэтому `Vec2` (8 байт) передаётся по значению быстро, а `Vec3` (12 байт) уже идёт через память. В Linux соглашение другое (System V: шесть регистров, иные правила для структур), и это одна из причин, почему бинарные библиотеки не переносятся между ОС.

## Время жизни локальных переменных

Кадр функции **снимается со стека** при возврате. Значит, все её локальные переменные прекращают существовать, а их память будет занята кадром следующей вызванной функции.

```cpp
int* dangerous() {
    int localHealth = 100;
    return &localHealth;   // вернуть АДРЕС локальной переменной (указатели — модуль 03)
}
```

После возврата из `dangerous` адрес указывает на место, где **была** `localHealth`. Скоро там окажутся данные другой функции. Обращение по такому адресу — неопределённое поведение, которое называется **висячий указатель** (dangling pointer). MSVC предупреждает: `C4172: возвращаемый адрес локальной переменной или временного`. Та же проблема со ссылками, мы встретим её в [[02.3 Ссылки и передача параметров#Не возвращай ссылку на локальную переменную|следующем уроке]].

> [!compare] В C#, Go и Python такой проблемы нет
> - **Go**: компилятор проводит **escape analysis**. Если адрес локальной переменной «утекает» из функции, переменная автоматически размещается в куче, а сборщик мусора следит за её жизнью.
> - **C#** и **Python**: объекты живут в куче, сборщик мусора не даст их удалить, пока на них есть ссылки.
> - **C++**: никакой автоматики. Локальная переменная живёт ровно до конца своего блока, и ответственность за то, чтобы на неё никто не ссылался дольше, лежит на тебе.

## Рекурсия

Функция может вызывать **саму себя**. Каждый вызов получает **свой** кадр на стеке со своими копиями локальных переменных.

```cpp
#include <print>

// n! = n * (n-1) * ... * 1
long long factorial(int n) {
    if (n <= 1) {
        return 1;                    // базовый случай: остановка рекурсии
    }
    return n * factorial(n - 1);     // рекурсивный случай
}

int main() {
    std::println("10! = {}", factorial(10));   // 3628800
    std::println("20! = {}", factorial(20));   // 2432902008176640000
}
```

Для `factorial(4)` стек растёт до четырёх кадров, а потом сворачивается:

```
factorial(4) → ждёт factorial(3)
  factorial(3) → ждёт factorial(2)
    factorial(2) → ждёт factorial(1)
      factorial(1) → возвращает 1        ← базовый случай
    factorial(2) → возвращает 2 * 1 = 2
  factorial(3) → возвращает 3 * 2 = 6
factorial(4) → возвращает 4 * 6 = 24
```

У рекурсивной функции обязательно есть **базовый случай**, при котором она не вызывает себя. Без него рекурсия бесконечна.

### Когда рекурсия естественна

Факториал проще посчитать циклом. Рекурсия хороша для задач, которые **сами рекурсивны**: обход дерева (папки внутри папок, объекты сцены внутри объектов), «разделяй и властвуй» (быстрая сортировка), перебор вариантов, заливка областей:

```cpp
// Залить область карты, начиная с клетки (x, y): все клетки '.', до которых можно дойти
void floodFill(std::vector<std::string>& map, int x, int y) {
    if (y < 0 || y >= static_cast<int>(map.size()) ||
        x < 0 || x >= static_cast<int>(map[y].size()) ||
        map[y][x] != '.') {
        return;                     // за картой, стена или уже залито
    }
    map[y][x] = '~';                // залить клетку
    floodFill(map, x + 1, y);       // и рекурсивно — четыре соседних
    floodFill(map, x - 1, y);
    floodFill(map, x, y + 1);
    floodFill(map, x, y - 1);
}
```

(Знак `&` в параметре означает передачу карты **по ссылке**, без копирования. Это тема следующего урока.) Такую функцию мы применим в практикуме, чтобы проверить, достижим ли выход в сгенерированной пещере.

### Переполнение стека

Стек **маленький**. Размер стека главного потока в Windows по умолчанию — **1 МБ**. Каждый рекурсивный вызов занимает десятки или сотни байт, и рекурсия глубиной в десятки тысяч вызовов исчерпывает стек:

```cpp
#include <print>

int depth = 0;

void dive() {
    ++depth;
    if (depth % 1000 == 0) {
        std::println("Глубина {}", depth);
    }
    dive();   // бесконечная рекурсия
}

int main() {
    dive();
}
```

Компилятор замечает проблему ещё при сборке: `warning C4717: dive: рекурсия на всех путях выполнения, функция вызовет переполнение стека`. В Debug программа напечатает несколько строк и упадёт с исключением **0xC00000FD — Stack overflow**. Отладчик покажет в Call Stack тысячи одинаковых кадров `dive`.

> [!warning] Бесконечная рекурсия в Release
> Я собрал этот пример в Release, и программа **не упала**: она спокойно напечатала «Глубина 3000000», «Глубина 3000001»… и работала бы вечно, хотя три миллиона кадров никак не помещаются в мегабайт стека. Оптимизатор увидел, что `dive` вызывает себя **последним действием** (это называется **хвостовой вызов**), и превратил рекурсию в обычный цикл, которому стек не нужен. Стандарт C++ такую оптимизацию не гарантирует, но и не запрещает. Мораль прежняя: Debug и Release — разные программы.

> [!engine] Рекурсия в движках
> Движки относятся к глубокой рекурсии с подозрением:
> - **Глубина часто зависит от данных.** Заливка области на карте 100 × 100 — до 10 000 уровней вложенности, на карте 2000 × 2000 — до 4 миллионов. Карты рисуют дизайнеры, и однажды кто-то нарисует огромную пустую комнату. Поэтому такие алгоритмы переписывают на **явный стек** (`std::vector` в куче вместо стека вызовов). Мы сделаем это в практикуме.
> - **У рабочих потоков стек меньше.** В системах задач (job system, модуль 14) задачи часто выполняются на маленьких стеках по 64 КБ, и рекурсия, которая работала в главном потоке, там падает.
> - Рекурсия **ограниченной** глубины — нормально: обход иерархии сцены (глубина 10–20), BSP-дерево уровня в Doom (глубина около 20). Кстати, оригинальный Doom рисовал уровень именно рекурсивным обходом BSP-дерева.

## Встраивание функций

Вызов функции — это не только `call` и `ret`. Это ещё передача аргументов, сохранение регистров и, главное, **барьер для оптимизатора**: он не видит, что происходит внутри вызываемой функции, и вынужден предполагать худшее.

Поэтому компилятор в Release **встраивает** (inline) маленькие функции: копирует их тело прямо в место вызова, как мы видели с `add`. После встраивания оптимизатор видит код целиком и может сделать гораздо больше: вычислить константы, убрать лишние проверки, векторизовать цикл.

- Решение о встраивании принимает **компилятор**, глядя на размер функции и частоту вызова.
- Встроить можно только функцию, **тело** которой видно в текущей единице трансляции. Функцию из другого `.cpp` обычный компилятор встроить не может (без оптимизации всей программы целиком, флаг `/GL`). Поэтому маленькие горячие функции (математика векторов) в движках определяют прямо в заголовках.
- В Debug встраивание выключено (`/Ob0`), иначе отладчик не смог бы зайти в функцию.
- Ключевое слово `inline` в современном C++ **не** означает «встрой». Его смысл связан с правилами линковки, и мы разберём его в [[02.5 Многофайловые программы и линковщик|уроке 02.5]]. Если очень нужно заставить MSVC встроить функцию, есть нестандартное `__forceinline`, и движки им пользуются, но в меру.

> [!engine] Цена вызова в цифрах
> Сам по себе вызов маленькой функции стоит порядка наносекунды. Это много или мало? Если вызывать функцию `length(Vec2)` для 100 000 частиц каждый кадр, то 100 000 × 1 нс = 0,1 мс, то есть меньше процента бюджета кадра. Но если из-за отсутствия встраивания цикл не векторизуется, потери вырастают в разы. Поэтому разработчики движков следят, чтобы горячая математика встраивалась, и проверяют это, читая ассемблер (модуль 11).

> [!try] Попробуй сам
> 1. Запусти программу с бесконечной рекурсией `dive` в Debug под отладчиком (`F5`). Посмотри на панель Call Stack в момент падения. Какой глубины удалось достичь?
> 2. Добавь в `dive` локальный массив `std::array<char, 1000> buffer{};`. Как изменилась максимальная глубина? Почему?
> 3. Напиши рекурсивную функцию `fibonacci(n)` по определению: `fib(n) = fib(n-1) + fib(n-2)`, `fib(0) = 0`, `fib(1) = 1`. Посчитай `fib(40)` и засеки время на глаз. Добавь глобальный счётчик вызовов. Сколько раз вызвалась функция? Почему так много?
> 4. ⭐ Перепиши `fibonacci` циклом и сравни.

> 1. Что хранится в кадре стека?
> 2. Где Windows x64 передаёт первые четыре целых аргумента? Где возвращается результат?
> 3. Почему создание локальной переменной почти ничего не стоит?
> 4. Почему нельзя возвращать адрес локальной переменной?
> 5. Сколько памяти по умолчанию у стека главного потока в Windows? Что произойдёт при слишком глубокой рекурсии?
> 6. Что такое встраивание и почему оно ускоряет код больше, чем просто на стоимость `call`?
> 7. Почему маленькие функции математики в движках пишут в заголовочных файлах?
>
> > [!success]- Ответы
> > 1. Адрес возврата, локальные переменные, сохранённые регистры, место для аргументов вызываемых функций.
> > 2. В регистрах RCX, RDX, R8, R9. Результат — в RAX (или XMM0 для дробных).
> > 3. Выделение места на стеке — это вычитание из регистра RSP, одна инструкция, и делается оно сразу для всех локальных переменных функции.
> > 4. После возврата кадр снят со стека, память будет переиспользована следующими вызовами. Обращение к ней — неопределённое поведение (висячий указатель).
> > 5. 1 МБ. Стек кончится, и программа упадёт с исключением 0xC00000FD (Stack overflow).
> > 6. Тело функции копируется в место вызова. Кроме экономии на `call`/`ret` и передаче аргументов, оптимизатор начинает видеть код целиком и может вычислить константы, убрать лишнее, векторизовать циклы.
> > 7. Чтобы тело было видно в каждой единице трансляции и компилятор мог их встроить.

> [!interview] Вопрос с собеседования
> **«Чем стек отличается от кучи?»** Один из самых частых вопросов. Пока ответ такой: стек — память под кадры вызовов, выделение и освобождение тривиальны (сдвиг указателя), время жизни строго привязано к области видимости, размер маленький (1 МБ). Куча — большая память для объектов произвольного времени жизни, выделение дороже (поиск свободного блока), освобождать нужно явно. Полный ответ дадим в модуле 03.
