# 03.4 Куча — new и delete

> [!abstract] О чём урок
> - зачем нужна куча, если есть стек;
> - `new` и `delete`, `new[]` и `delete[]`;
> - **утечки памяти** и как их ловит отладочная куча MSVC;
> - **висячие указатели** и двойное удаление;
> - **владение**: кто отвечает за удаление объекта;
> - сколько стоит выделение памяти: замер «миллион `new`» против одного вектора.

## Зачем куча

Стек быстрый и удобный, но у него три ограничения:
1. **Время жизни привязано к блоку.** Локальная переменная умирает при выходе из функции. А враг, созданный функцией `spawnEnemy`, должен жить, пока его не убьют.
2. **Размер должен быть известен при компиляции.** Нельзя написать `int scores[playerCount];`, где `playerCount` прочитан из файла. (MSVC такого не допускает в принципе, хоть некоторые компиляторы и разрешают это как расширение.)
3. **Стек маленький**: 1 МБ. Текстура 2048 × 2048 × 4 байта — это 16 МБ.

**Куча** (heap, или динамическая память) снимает все три ограничения: объект живёт, пока его явно не удалят, размер может быть любым и вычисляться во время работы, а доступна вся свободная память компьютера.

Ты уже пользовался кучей, не замечая этого: `std::vector` и `std::string` хранят свои буферы именно там. Теперь посмотрим, как это делается вручную.

## `new` и `delete`

```cpp
#include <print>
#include <string>

struct Enemy {
    std::string name;
    int health = 100;
};

int main() {
    Enemy* imp = new Enemy{"Imp", 60};   // создать объект в куче, получить указатель
    imp->health -= 25;
    std::println("{}: {}", imp->name, imp->health);   // Imp: 35

    delete imp;                          // уничтожить объект и вернуть память
    imp = nullptr;                       // хорошая привычка: указатель больше никуда не указывает
}
```

- `new T{...}` выделяет память в куче, **создаёт** в ней объект типа `T` (с инициализацией из фигурных скобок) и возвращает указатель на него.
- `delete p` **уничтожает** объект (для `Enemy` это освободит и буфер строки `name`) и возвращает память куче.
- `delete nullptr` ничего не делает: это безопасно.

Варианты инициализации:

```cpp
int* a = new int;        // значение НЕ инициализировано (мусор)
int* b = new int{};      // 0
int* c = new int{42};    // 42
Enemy* e = new Enemy{};  // поля получают значения по умолчанию
```

### Массивы: `new[]` и `delete[]`

```cpp
int count = computeEnemyCount();      // известно только во время работы
int* healths = new int[count]{};      // массив из count нулей
healths[0] = 100;
delete[] healths;                     // обязательно с []!
```

> [!ub] `delete` и `delete[]` не взаимозаменяемы
> Память, выделенную `new[]`, нужно освобождать `delete[]`, а выделенную `new` — просто `delete`. Перепутать — неопределённое поведение: для массива объектов `delete` без скобок вызовет деструктор только у первого элемента, а для кучи это может испортить её внутренние структуры. Компилятор не предупреждает, и даже AddressSanitizer в MSVC этого по умолчанию не ловит (я проверил).

> [!compare] Как в других языках
> - **C#**: `new Enemy()` тоже выделяет объект в куче, но удалять его не нужно: сборщик мусора сделает это, когда ссылок не останется.
> - **Go**: `&Enemy{}` или `new(Enemy)`. Компилятор сам решает, куда поместить объект: на стек или в кучу (escape analysis), а удаляет GC.
> - **C++**: где разместить объект, решаешь ты, и удалить его тоже должен ты.

## Утечки памяти

Если объект из кучи не удалить, память остаётся занятой до конца программы. Это **утечка** (memory leak). Одна утечка в 12 байт безвредна, но утечка в функции, которая вызывается каждый кадр, через час съест всю память.

Отладочная куча MSVC умеет находить утечки. Достаточно включить проверку в начале `main`:

```cpp
#include <crtdbg.h>
#include <print>

struct Enemy {
    int health = 100;
    int damage = 10;
};

int main() {
    // Debug-сборка: при выходе из программы CRT перечислит все неосвобождённые блоки.
    // Отчёт печатаем в консоль (по умолчанию он уходит только в окно отладчика).
    _CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);
    _CrtSetReportMode(_CRT_WARN, _CRTDBG_MODE_FILE);
    _CrtSetReportFile(_CRT_WARN, _CRTDBG_FILE_STDERR);

    Enemy* boss = new Enemy{5000, 50};
    int* ammo = new int[3]{12, 8, 50};
    std::println("Босс: {} HP, патронов в первом слоте: {}", boss->health, ammo[0]);

    delete boss;
    // delete[] ammo;  — забыли!
}
```

Вывод в Debug:

```
Босс: 5000 HP, патронов в первом слоте: 12
Detected memory leaks!
Dumping objects ->
{185} normal block at 0x000002D7C5F5F550, 12 bytes long.
 Data: <        2   > 0C 00 00 00 08 00 00 00 32 00 00 00
Object dump complete.
```

Читаем отчёт:
- **12 bytes long** — утёк блок размером 12 байт: три `int`.
- **Data**: содержимое блока. `0C 00 00 00` = 12, `08 00 00 00` = 8, `32 00 00 00` = 50. Наш массив патронов, байты в порядке little-endian ([[01.2 Переменные и фундаментальные типы#Как число лежит в памяти|урок 01.2]]).
- **{185}** — порядковый номер выделения памяти с начала программы. Это самое ценное: если добавить в начало `main` вызов `_CrtSetBreakAlloc(185);`, то при следующем запуске под отладчиком программа **остановится ровно в момент выделения** утёкшего блока, и Call Stack покажет, кто его выделил. (Номер стабилен, если программа при каждом запуске выделяет память в одном и том же порядке.)

В Release все эти вызовы превращаются в пустоту: отладочная куча существует только в Debug.

> [!tip] Включай проверку утечек всегда
> Три строки `_CrtSet...` стоит вставлять в начало `main` каждой учебной программы, где есть `new`. В движке Ember мы сделаем это частью инициализации в Debug-сборке.

## Висячие указатели и двойное удаление

После `delete` объекта нет, но **указатель на него остался**, и в нём всё тот же адрес. Это висячий указатель ([[02.3 Ссылки и передача параметров#Висячие ссылки|урок 02.3]]), и обращение через него — неопределённое поведение:

```cpp
#include <print>

struct Enemy {
    int health = 100;
};

int main() {
    Enemy* imp = new Enemy{60};
    delete imp;                    // враг убит, память освобождена
    int hp = imp->health;          // ...но указатель остался
    std::println("Здоровье: {}", hp);
}
```

В Debug-сборке у меня напечаталось:
```
Здоровье: -572662307
```

`-572662307` — это `0xDDDDDDDD`, «магическое число» освобождённой памяти из [[00.6 Отладчик — главный инструмент#Магические числа MSVC|урока 00.6]]. Отладочная куча заполняет каждый освобождённый блок байтами `0xDD`, чтобы такие ошибки сразу бросались в глаза. В Release программа, скорее всего, напечатает 60: память ещё не переиспользовали. Код «работает», пока однажды не перестанет.

**Двойное удаление** — вызвать `delete` для одного указателя дважды — тоже UB, обычно портящее внутренние структуры кучи. Присваивание `imp = nullptr;` после `delete` защищает от двойного удаления **через этот** указатель (ведь `delete nullptr` безопасен). Но если копии указателя хранятся где-то ещё, они по-прежнему висят.

> [!warning] Самые опасные ошибки в C++
> Утечки, висячие указатели и двойное удаление — три главных источника падений и уязвимостей в программах на C и C++. По данным Microsoft и Google, около **70%** серьёзных уязвимостей в их продуктах связаны именно с ошибками работы с памятью. Поэтому весь современный C++ построен вокруг того, чтобы `new` и `delete` руками почти не писать. Об этом — модули 04 и 05.

## Владение

Корень всех трёх проблем — вопрос «**кто удалит этот объект?**». Ответ на него называется **владением** (ownership):

```cpp
#include <print>
#include <string>

struct Enemy {
    std::string name;
    int health = 100;
};

// Функция создаёт врага в куче и ВОЗВРАЩАЕТ ВЛАДЕНИЕ вызывающему коду
Enemy* spawnEnemy(const std::string& name, int health) {
    return new Enemy{name, health};
}

// Функция только СМОТРИТ на врага: она не владеет им и не удаляет
void printEnemy(const Enemy* enemy) {
    std::println("{}: {}", enemy->name, enemy->health);
}

int main() {
    Enemy* boss = spawnEnemy("Cyberdemon", 4000);   // теперь main — владелец
    printEnemy(boss);
    delete boss;                                     // владелец и удаляет
}
```

Беда в том, что `Enemy*` выглядит **одинаково** и у владеющего, и у невладеющего указателя. По подписи `Enemy* spawnEnemy(...)` не видно, что результат обязательно нужно удалить. Программисты пишут об этом в комментариях и документации, а потом забывают.

Решение C++ — сделать владение частью **типа**: `std::unique_ptr<Enemy>` — «я владею и удалю сам», `Enemy*` или `Enemy&` — «я только смотрю». Компилятор следит за правилами, а удаление происходит автоматически. Это тема модулей 04 (RAII) и 05 (умные указатели). А пока, работая с `new` вручную, мы учимся понимать, **что** именно автоматизируют эти инструменты.

## Сколько стоит `new`

Выделение в куче — не бесплатная операция. Сравним два способа хранить миллион частиц:

```cpp
#include <chrono>
#include <print>
#include <vector>

struct Particle {
    float x = 0.0f;
    float y = 0.0f;
    float vx = 1.0f;
    float vy = 1.0f;
};

int main() {
    constexpr int count = 1'000'000;

    // 1. Каждая частица — отдельное выделение в куче
    auto start = std::chrono::steady_clock::now();
    std::vector<Particle*> scattered;
    scattered.reserve(count);
    for (int i = 0; i < count; ++i) {
        scattered.push_back(new Particle{});
    }
    for (Particle* p : scattered) {
        delete p;
    }
    auto mid = std::chrono::steady_clock::now();

    // 2. Все частицы одним блоком
    std::vector<Particle> packed(count);
    auto finish = std::chrono::steady_clock::now();

    auto ms = [](auto a, auto b) { return std::chrono::duration<double, std::milli>(b - a).count(); };
    std::println("{} отдельных new/delete: {:.1f} мс", count, ms(start, mid));
    std::println("Один vector на {} частиц:  {:.1f} мс", count, ms(mid, finish));
    std::println("Контроль: {}", packed[count / 2].vx);
}
```

(Строка с `auto ms = [](auto a, auto b) {...}` — это **лямбда**, маленькая безымянная функция; их мы разберём в модуле 06. Здесь она просто переводит разницу времён в миллисекунды.)

Результаты на моей машине:

| | 1 000 000 × `new`/`delete` | один `vector` |
|---|---|---|
| Release | **~70 мс** | **~2,4 мс** |
| Debug | ~270 мс | ~15 мс |

Почти **в 30 раз** дороже, хотя данных столько же. И это без учёта того, что потом частицы, разбросанные по куче, медленнее и **обходить**: процессору приходится прыгать по памяти, а не читать её подряд (модуль 11).

> [!deep] Под капотом: что делает `new`
> 1. `new Particle{}` вызывает функцию `operator new(sizeof(Particle))`.
> 2. Та вызывает `malloc` из C-рантайма.
> 3. `malloc` обращается к **куче Windows** (`HeapAlloc`): ищет свободный блок подходящего размера в своих списках, помечает его занятым, записывает служебный заголовок. Если места нет, просит у ОС новые страницы через `VirtualAlloc`.
> 4. Только после этого в выделенной памяти **конструируется** объект.
>
> `delete` проходит этот путь в обратную сторону: деструктор, `operator delete`, `free`, `HeapFree`, который возвращает блок в списки свободных и, возможно, склеивает его с соседями.
>
> У каждого блока есть накладные расходы: служебный заголовок и выравнивание размера блока до 16 байт. Частица из четырёх `float` (16 байт) в отдельном блоке реально занимает 32 байта и больше. В Debug ещё больше: отладочная куча добавляет к каждому блоку свой заголовок и по 4 «защитных» байта `0xFD` с каждой стороны, чтобы ловить выход за границы, и заполняет новую память байтами `0xCD`.

> [!engine] Куча и движки
> - **Правило горячего цикла**: в коде, который выполняется каждый кадр, выделений памяти быть не должно. Буферы заводятся заранее и переиспользуются ([[01.7 Первые составные типы — array, vector, struct#Вектор — динамический массив|урок 01.7]]).
> - **Фрагментация.** После тысяч выделений и освобождений разного размера куча превращается в решето: свободной памяти много, но кусками, и большой блок выделить не удаётся. Для консольной игры, которая работает часами без перезапуска, это реальная угроза.
> - **Свои аллокаторы.** Поэтому движки заменяют общую кучу специализированными аллокаторами: «арена на кадр», которая сбрасывается целиком в конце кадра одним присваиванием; пулы объектов одного размера; стековые аллокаторы для загрузки уровня. Unreal Engine вообще подменяет глобальный `operator new` на свою систему `FMalloc`. Мы напишем такие аллокаторы в модуле 12.

> [!quiz]- Проверь себя
> 1. Назови три ограничения стека, которые снимает куча.
> 2. Чем `new int` отличается от `new int{}`?
> 3. Что будет, если память из `new[]` освободить через `delete`?
> 4. Как найти, где была выделена утёкшая память?
> 5. Почему после `delete p;` полезно написать `p = nullptr;` и почему это не полная защита?
> 6. Что такое владение и почему `Enemy*` плохо его выражает?
> 7. Почему миллион отдельных `new` медленнее одного вектора на миллион элементов?
>
> > [!success]- Ответы
> > 1. Время жизни, привязанное к блоку; размер, известный при компиляции; маленький объём (1 МБ).
> > 2. `new int` оставляет значение неинициализированным, `new int{}` инициализирует нулём.
> > 3. Неопределённое поведение: возможна порча кучи, деструкторы элементов массива (кроме первого) не вызовутся.
> > 4. Включить отчёт `_CrtSetDbgFlag(... | _CRTDBG_LEAK_CHECK_DF)`, взять номер блока в фигурных скобках и вызвать `_CrtSetBreakAlloc(номер)`: отладчик остановится в момент выделения.
> > 5. `delete nullptr` безопасен, поэтому повторное удаление через этот указатель ничего не сломает, а обращение к нему упадёт явно. Но другие копии указателя по-прежнему висят.
> > 6. Владение — ответственность за удаление объекта. По типу `Enemy*` нельзя понять, владеет указатель объектом или только смотрит на него.
> > 7. Каждый `new` ищет свободный блок, пишет служебные данные и платит накладные расходы; один вектор делает одно выделение на все элементы. К тому же разбросанные по куче объекты медленнее обходить.

> [!interview] Вопрос с собеседования
> **«Что такое утечка памяти и как её найти?»** Ответ: выделенная память, которую больше никто не освободит, обычно потому, что потерян последний указатель на неё. Инструменты: отладочная куча CRT (`_CrtDumpMemoryLeaks`, номер выделения и `_CrtSetBreakAlloc`), LeakSanitizer (в Clang/GCC), Valgrind (Linux), профилировщики памяти. Профилактика: RAII и умные указатели, чтобы ручного `delete` не было вообще.
