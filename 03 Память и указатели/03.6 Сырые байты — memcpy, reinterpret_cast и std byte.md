# 03.6 Сырые байты — memcpy, reinterpret_cast и std::byte

> [!abstract] О чём урок
> - любой объект — это последовательность байтов; как на неё посмотреть;
> - `std::byte` и `std::span` байтов;
> - `memcpy`, `memmove`, `memset` и для каких типов они допустимы;
> - `reinterpret_cast` и **правило строгого совмещения**: как правильно «переосмыслить» биты (`std::bit_cast`);
> - разбираем `float` на биты и воскрешаем легендарный быстрый обратный корень из Quake III;
> - сохраняем данные в двоичный файл и читаем обратно.
>
> Это язык, на котором движок разговаривает с файлами, сетью и видеокартой: всё, что уходит из программы или приходит в неё, — это просто байты.

## Объект — это байты

Каждый объект занимает `sizeof(T)` байт подряд, и на эти байты можно посмотреть. Напишем функцию, которая печатает байты в шестнадцатеричном виде (**хекс-дамп**):

```cpp
#include <cstddef>
#include <print>
#include <span>

struct Pickup {
    char kind;      // тип подбираемого предмета
    int amount;     // количество
};

void hexDump(std::span<const std::byte> bytes) {
    for (std::byte b : bytes) {
        std::print("{:02x} ", std::to_integer<int>(b));
    }
    std::println("");
}

int main() {
    Pickup ammo{'A', 25};
    std::println("sizeof(Pickup) = {}", sizeof(Pickup));
    hexDump(std::as_bytes(std::span(&ammo, 1)));

    int value = 0x12345678;
    hexDump(std::as_bytes(std::span(&value, 1)));
}
```

Вывод в Debug:

```
sizeof(Pickup) = 8
41 cc cc cc 19 00 00 00
78 56 34 12
```

Разбираем:
- `41` — это `'A'` (код 65 = 0x41);
- `cc cc cc` — **заполнение** (padding) между `char` и `int` ([[01.7 Первые составные типы — array, vector, struct#Под капотом выравнивание и дыры в структурах|урок 01.7]]). Компилятор его не инициализирует, а Debug-сборка заливает стек байтами `0xCC`. Вот они, «дыры» в структуре, своими глазами;
- `19 00 00 00` — число 25, младший байт первым (little-endian);
- `78 56 34 12` — наш старый знакомый `0x12345678`.

Новые инструменты в этом коде:
- **`std::byte`** (C++17, заголовок `<cstddef>`) — тип «просто байт». В отличие от `char` и `unsigned char`, это **не число**: его нельзя случайно сложить или вывести как букву. Только побитовые операции и явное `std::to_integer<int>(b)`. Так тип сам говорит: «здесь сырые данные».
- **`std::as_bytes(span)`** превращает `std::span<T>` в `std::span<const std::byte>`: вид на те же данные как на байты. `std::span(&ammo, 1)` — вид на «массив» из одного объекта.

> [!deep] Почему так можно
> В C++ действует жёсткое правило: обращаться к объекту можно только через указатель (или ссылку) его собственного типа. Но есть исключение: **через `char`, `unsigned char` и `std::byte` можно читать байты любого объекта**. Именно поэтому `as_bytes` законен, а все функции работы с памятью (`memcpy`, `fwrite`, сетевая отправка) принимают байты или `void*`.

## `memcpy`, `memmove`, `memset`

Функции из заголовка `<cstring>`, пришедшие из C, работают с памятью как с байтами:

| Функция | Что делает |
|---|---|
| `std::memcpy(dst, src, n)` | Копирует `n` байт из `src` в `dst`. Области **не должны перекрываться**. |
| `std::memmove(dst, src, n)` | То же, но корректно работает при перекрытии областей (чуть медленнее). |
| `std::memset(dst, value, n)` | Заполняет `n` байт значением `value` (обычно нулём). |
| `std::memcmp(a, b, n)` | Сравнивает `n` байт. |

```cpp
float source[4] = {1.0f, 2.0f, 3.0f, 4.0f};
float target[4];
std::memcpy(target, source, sizeof(source));    // скопировать 16 байт

int grid[64];
std::memset(grid, 0, sizeof(grid));             // обнулить
```

Компилятор знает эти функции и превращает их в оптимальный машинный код: `memcpy` на 16 байт станет парой инструкций, а на мегабайт — вызовом высокооптимизированной функции с SIMD-инструкциями.

> [!ub] `memcpy` только для «простых» типов
> `memcpy` копирует байты и ничего не знает о смысле объекта. Для `int`, `float`, `Vec2`, `Pickup` этого достаточно. Но `std::string` внутри хранит **указатель** на буфер в куче. Если скопировать строку побайтно, у двух строк окажется указатель на **один** буфер, и при уничтожении обеих буфер будет освобождён дважды. Двойное освобождение, UB.
>
> Типы, которые можно безопасно копировать побайтно, называются **тривиально копируемыми** (trivially copyable). Проверить это может сам компилятор:
> ```cpp
> #include <type_traits>
> static_assert(std::is_trivially_copyable_v<Pickup>);       // ок
> static_assert(std::is_trivially_copyable_v<std::string>);  // ошибка компиляции
> ```
> `static_assert` — проверка, которую выполняет компилятор; если условие ложно, сборка остановится. Ставь её рядом с каждым `memcpy` структуры.

## `reinterpret_cast` и строгое совмещение

Иногда хочется посмотреть на биты `float` как на `std::uint32_t`. Первое, что приходит в голову:

```cpp
float speed = 1.0f;
std::uint32_t* bits = reinterpret_cast<std::uint32_t*>(&speed);   // «считай, что тут uint32_t»
std::uint32_t value = *bits;                                       // UB!
```

`reinterpret_cast` — самое опасное из приведений: «возьми этот адрес и считай, что там лежит объект другого типа». Код скомпилируется, и в MSVC даже, скорее всего, сработает. Но это нарушение **правила строгого совмещения** (strict aliasing): обращаться к объекту через указатель несовместимого типа — неопределённое поведение. GCC и Clang при оптимизации опираются на это правило («запись через `uint32_t*` не может изменить `float`») и могут переставить чтения и записи так, что результат окажется неверным.

Правильные способы переосмыслить биты:

```cpp
#include <bit>
auto bits = std::bit_cast<std::uint32_t>(speed);    // C++20: чисто и законно

std::uint32_t bits2;
std::memcpy(&bits2, &speed, sizeof(bits2));         // классика: копия байтов
```

Оба варианта компилятор превращает в одну инструкцию, накладных расходов нет. `std::bit_cast` требует, чтобы оба типа были одного размера и тривиально копируемы, и проверяет это при компиляции.

> [!tip] Когда `reinterpret_cast` всё-таки нужен
> - Преобразовать указатель в «указатель на байты» для `memcpy`, файлов и сети (`reinterpret_cast<const char*>(&data)`): через `char` и `std::byte` читать можно ([[#Объект — это байты|см. выше]]).
> - Указатель в целое и обратно (`std::uintptr_t`), как мы делали в [[03.1 Карта памяти процесса#Стек растёт вниз|уроке 03.1]].
> - Работа с API, которые возвращают «сырую» память: WinAPI, Direct3D, отображение файлов в память.
>
> Во всех остальных случаях ищи другой способ.

## Разбираем `float` на биты

Вспомним устройство `float` из [[01.2 Переменные и фундаментальные типы#Числа с плавающей точкой|урока 01.2]]: 1 бит знака, 8 бит порядка, 23 бита мантиссы. Теперь его можно увидеть:

```cpp
#include <bit>
#include <cstdint>
#include <print>

void printFloatBits(float value) {
    auto bits = std::bit_cast<std::uint32_t>(value);
    std::uint32_t sign = bits >> 31;
    std::uint32_t exponent = (bits >> 23) & 0xFF;
    std::uint32_t mantissa = bits & 0x7FFFFF;
    std::println("{:>8} = {:#010x}  знак {}  порядок {:3} (2^{:>3})  мантисса {:#08x}",
                 value, bits, sign, exponent, static_cast<int>(exponent) - 127, mantissa);
}

int main() {
    for (float f : {1.0f, -2.5f, 0.1f, 1024.0f}) {
        printFloatBits(f);
    }
}
```

```
       1 = 0x3f800000  знак 0  порядок 127 (2^  0)  мантисса 0x000000
    -2.5 = 0xc0200000  знак 1  порядок 128 (2^  1)  мантисса 0x200000
     0.1 = 0x3dcccccd  знак 0  порядок 123 (2^ -4)  мантисса 0x4ccccd
    1024 = 0x44800000  знак 0  порядок 137 (2^ 10)  мантисса 0x000000
```

- Порядок хранится **со смещением 127**: 127 означает 2⁰, 128 — 2¹, 123 — 2⁻⁴.
- Мантисса хранит дробную часть числа вида `1.xxx` в двоичной записи; ведущая единица не хранится, она подразумевается. `-2.5 = -1.25 × 2¹`, и `0.25` в двоичной — `.01`, отсюда мантисса `0x200000` (бит 21 из 23).
- `0.1` — та самая бесконечная двоичная дробь: `0x4ccccd` — это повторяющийся узор `1100 1100…`, округлённый в последнем бите.

### Легенда: быстрый обратный корень

В исходниках Quake III Arena (1999) нашли функцию, которая стала легендой программистов движков. Она вычисляет 1/√x (нужно для нормализации векторов в освещении), не вызывая ни деления, ни корня:

```cpp
#include <bit>
#include <cmath>
#include <cstdint>
#include <print>

float fastInvSqrt(float x) {
    float half = 0.5f * x;
    auto i = std::bit_cast<std::uint32_t>(x);   // биты float как целое число
    i = 0x5f3759df - (i >> 1);                  // магия
    float y = std::bit_cast<float>(i);          // обратно во float: первое приближение
    y = y * (1.5f - half * y * y);              // одна итерация метода Ньютона
    return y;
}

int main() {
    for (float x : {1.0f, 2.0f, 10.0f, 100.0f}) {
        std::println("{:6} {:.6f} {:.6f}", x, fastInvSqrt(x), 1.0f / std::sqrt(x));
    }
}
```

```
     1 0.998307 1.000000
     2 0.706930 0.707107
    10 0.315686 0.316228
   100 0.099845 0.100000
```

Погрешность меньше 0,2%. Как это работает? Биты `float`, прочитанные как целое число, — это примерно масштабированный **логарифм** числа (порядок стоит в старших битах). Сдвиг вправо делит логарифм на 2 (это корень), вычитание из константы меняет знак (это обратная величина), а магическая константа `0x5f3759df` подправляет погрешность. Потом одна итерация метода Ньютона уточняет результат.

> [!engine] История и мораль
> В оригинале биты читались через `*(long*)&y`, то есть ровно тем способом, который сегодня считается нарушением строгого совмещения. Тогдашние компиляторы так не оптимизировали. Сегодня тот же трюк пишется через `std::bit_cast` и полностью законен.
>
> Практического смысла в нём больше нет: у современных процессоров есть инструкция `rsqrtss`, которая делает то же самое быстрее и точнее, и компиляторы сами используют её. Но трюк отлично показывает, как мыслили программисты движков: **знать, как устроены данные на уровне битов, и использовать это**.

## Выравнивание

У каждого типа есть **выравнивание** — число, которому должен быть кратен его адрес: `alignof(int) == 4`, `alignof(double) == 8`. Отсюда и заполнение в структурах.

> [!ub] Не читай типы из произвольного места буфера через указатель
> ```cpp
> std::byte buffer[16];
> // ... buffer заполнен данными из файла ...
> int value = *reinterpret_cast<int*>(buffer + 1);   // UB: и совмещение, и адрес не кратен 4
> ```
> На x86 невыровненное чтение обычно «просто работает» (немного медленнее), но это UB, а на других процессорах и с SIMD-инструкциями приводит к падению. Правильно — скопировать байты в настоящую переменную:
> ```cpp
> int value;
> std::memcpy(&value, buffer + 1, sizeof(value));
> ```
> Компилятор и здесь сгенерирует одну инструкцию.

## Сохраняем в двоичный файл

Соберём всё вместе: сохраним состояние игрока в файл и прочитаем обратно. Для этого нужны две функции: дописать байты в буфер и прочитать байты из буфера с проверкой границ.

```cpp
#include <cstddef>
#include <cstdint>
#include <cstring>
#include <filesystem>
#include <fstream>
#include <print>
#include <vector>

// Дописать в конец буфера size байт, начиная с адреса data
void appendBytes(std::vector<std::byte>& buffer, const void* data, std::size_t size) {
    const auto* first = static_cast<const std::byte*>(data);
    buffer.insert(buffer.end(), first, first + size);   // диапазон указателей [first, first + size)
}

// Прочитать size байт из буфера с позиции offset. false — если данных не хватает.
bool readBytes(const std::vector<std::byte>& buffer, std::size_t& offset, void* out, std::size_t size) {
    if (offset + size > buffer.size()) {
        return false;
    }
    std::memcpy(out, buffer.data() + offset, size);
    offset += size;
    return true;
}

struct PlayerState {
    float x = 0.0f;
    float y = 0.0f;
    std::int32_t health = 100;
    std::int32_t ammo = 50;
};

int main() {
    // ---------- Сохранение ----------
    PlayerState saved{12.5f, -3.0f, 87, 23};

    std::vector<std::byte> buffer;
    appendBytes(buffer, &saved.x, sizeof(saved.x));
    appendBytes(buffer, &saved.y, sizeof(saved.y));
    appendBytes(buffer, &saved.health, sizeof(saved.health));
    appendBytes(buffer, &saved.ammo, sizeof(saved.ammo));

    {
        std::ofstream out("player.sav", std::ios::binary);
        out.write(reinterpret_cast<const char*>(buffer.data()), static_cast<std::streamsize>(buffer.size()));
    }   // здесь файл закрывается
    std::println("Записано {} байт в {}", buffer.size(), std::filesystem::absolute("player.sav").string());

    // ---------- Загрузка ----------
    std::ifstream in("player.sav", std::ios::binary | std::ios::ate);   // ate: встать в конец файла
    if (!in) {
        std::println("Не удалось открыть файл");
        return 1;
    }
    auto size = static_cast<std::size_t>(in.tellg());   // позиция в конце = размер файла
    in.seekg(0);                                        // вернуться в начало
    std::vector<std::byte> loadedBytes(size);
    in.read(reinterpret_cast<char*>(loadedBytes.data()), static_cast<std::streamsize>(size));

    PlayerState loaded;
    std::size_t offset = 0;
    bool ok = readBytes(loadedBytes, offset, &loaded.x, sizeof(loaded.x)) &&
              readBytes(loadedBytes, offset, &loaded.y, sizeof(loaded.y)) &&
              readBytes(loadedBytes, offset, &loaded.health, sizeof(loaded.health)) &&
              readBytes(loadedBytes, offset, &loaded.ammo, sizeof(loaded.ammo));
    if (!ok) {
        std::println("Файл повреждён");
        return 1;
    }
    std::println("Загружено: позиция ({}, {}), здоровье {}, патроны {}", loaded.x, loaded.y, loaded.health, loaded.ammo);
}
```

```
Записано 16 байт в D:\SourceCode\CPPJourney\practice\player.sav
Загружено: позиция (12.5, -3), здоровье 87, патроны 23
```

Новое здесь:
- **`std::ofstream`** и **`std::ifstream`** из `<fstream>` — файловые потоки для записи и чтения. Флаг `std::ios::binary` отключает преобразование переводов строк (в текстовом режиме Windows превратила бы байт `0x0A` в `0x0D 0x0A` и испортила данные).
- `write` и `read` принимают `const char*`/`char*` и количество байт: отсюда `reinterpret_cast` к указателю на `char`, это разрешённый случай.
- Файл закрывается автоматически, когда переменная потока выходит из области видимости. Поэтому запись обёрнута в отдельный блок `{ }`: к моменту чтения файл уже закрыт и все данные записаны. Это **RAII**, главная идея следующего модуля.
- `std::filesystem::absolute` показывает полный путь, куда попал файл. Он зависит от **рабочей папки** программы: при запуске по `F5` это папка `practice`, а при запуске через `Ctrl+Shift+F5` — папка с `.exe` (`build\bin\Debug`).
- `buffer.insert(buffer.end(), first, first + size)` — вставка **диапазона указателей**: та самая пара «начало–конец» из [[03.3 Массивы и арифметика указателей#Обход парой указателей|урока 03.3]].

> [!question] Почему не записать всю структуру одним `memcpy`?
> Для `PlayerState` это сработало бы: все поля по 4 байта, заполнения нет, тип тривиально копируемый. Но в общем случае так лучше не делать:
> - **заполнение** попадёт в файл: в файле окажутся случайные байты (`cc cc cc`), и два сохранения одинаковых данных будут различаться;
> - добавишь поле в середину структуры — старые сохранения перестанут читаться;
> - структура с `std::string` или `std::vector` внутри вообще не копируется побайтно;
> - другой компилятор или платформа могут разложить поля иначе.
>
> Запись поле за полем даёт полный контроль над форматом файла. В практикуме мы добавим к формату заголовок, версию и строки.

> [!engine] Двоичные форматы в движках
> Движки хранят ресурсы (модели, текстуры, уровни) в собственных двоичных форматах, «запечённых» специально для загрузки: никакого разбора текста, данные лежат в файле ровно в том виде, в каком нужны в памяти. Предельный вариант — **загрузка на месте** (load in place): файл целиком читается в память одним вызовом, внутренние указатели хранятся как смещения от начала файла и после загрузки «исправляются» в настоящие адреса. Так грузились уровни на консолях, где каждая секунда загрузки на счету. В любом таком формате обязательно есть **магическое число** в начале (чтобы отличить свой файл от чужого), **версия** и часто **контрольная сумма**.

> 4. Что такое правило строгого совмещения? Как законно получить биты `float`?
> 5. Почему чтение `int` по адресу `buffer + 1` — проблема дважды?
> 6. Зачем флаг `std::ios::binary`?
> 7. Почему не стоит сохранять структуру одним `memcpy`?
>
> > [!success]- Ответы
> > 1. `char`, `unsigned char` и `std::byte`.
> > 2. `std::byte` — не числовой тип: с ним нельзя делать арифметику и его нельзя случайно вывести как символ. Только побитовые операции и явное преобразование в число.
> > 3. Внутри строки указатель на буфер в куче. После побайтной копии два объекта будут владеть одним буфером, и при уничтожении он освободится дважды.
> > 4. К объекту можно обращаться только через указатель его типа (или `char`/`std::byte`); иначе UB, и оптимизатор этим пользуется. Законно: `std::bit_cast<std::uint32_t>(f)` или `memcpy` в переменную `std::uint32_t`.
> > 5. Нарушается строгое совмещение (байты читаются как `int` через `reinterpret_cast`) и адрес не выровнен по 4. Правильно — `memcpy` в переменную.
> > 6. Чтобы поток не преобразовывал символы перевода строки и записывал байты как есть.
> > 7. В файл попадёт заполнение со случайными байтами, формат станет зависеть от раскладки структуры и компилятора, а типы с указателями внутри вообще нельзя копировать побайтно.
