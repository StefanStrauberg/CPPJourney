# 03.5 Неопределённое поведение и AddressSanitizer

> [!abstract] О чём урок
> - каталог ошибок памяти: что считается неопределённым поведением;
> - какие инструменты MSVC что ловят: предупреждения, `/RTC1`, отладочная куча, проверки STL;
> - подключаем **AddressSanitizer** к проекту курса отдельным пресетом CMake;
> - читаем отчёты ASan на настоящих ошибках;
> - как ASan устроен внутри и чего он не умеет.
>
> Этот урок — твоя страховка на весь оставшийся курс. Каждый раз, когда программа ведёт себя странно, первым делом собирай её с ASan.

## Каталог ошибок памяти

| Ошибка | Пример | Что обычно происходит |
|---|---|---|
| **Выход за границы** (buffer overflow) | `int a[4]; a[4] = 1;` | Тихая порча соседних данных |
| **Обращение после освобождения** (use-after-free) | `delete p; p->hp = 0;` | Порча данных, которые уже принадлежат другому объекту |
| **Двойное освобождение** (double free) | `delete p; delete p;` | Порча внутренних структур кучи, падение позже и в другом месте |
| **Висячая ссылка на стек** (use-after-return) | вернуть адрес локальной переменной | Чтение данных чужого кадра стека |
| **Разыменование `nullptr`** | `Enemy* e = nullptr; e->hp;` | Падение `0xC0000005` (самый «честный» случай) |
| **Чтение неинициализированной памяти** | `int x; use(x);` | Случайные значения, разное поведение Debug/Release |
| **Несовпадение `new[]`/`delete`** | `delete` для массива | Порча кучи |
| **Утечка** (не UB, но баг) | `new` без `delete` | Рост потребления памяти |

Общая черта почти всех строк в правом столбце: ошибка **не проявляется в месте, где её совершили**. Программа портит память в одной функции, а падает через полчаса в совершенно другой, когда кто-то прочитает испорченные данные. Отладчик в момент падения показывает невиновный код. Поэтому такие баги ищут не отладчиком, а **инструментами, которые ловят ошибку в момент совершения**.

## Что ловят инструменты MSVC

| Инструмент | Ловит | Когда работает | Цена |
|---|---|---|---|
| Предупреждения `/W4` | неинициализированные переменные (простые случаи), возврат адреса локальной | при компиляции | бесплатно |
| `/RTC1` | использование неинициализированных локальных, часть порчи стека | Debug | мало |
| Отладочная куча CRT | утечки (отчёт при выходе), заливка `0xCD`/`0xDD`, порча защитных байт `0xFD` (обнаруживается при `delete`) | Debug | мало |
| Проверки STL | выход за границы `vector`, `array`, `string` через `[]`, испорченные итераторы | Debug | заметно |
| **AddressSanitizer** | выход за границы в куче, на стеке и в глобальных данных; use-after-free; double free; use-after-return | отдельная сборка | ~2× по скорости и памяти |

Первые четыре уже работают в нашей Debug-сборке: ты видел их в действии в практикуме 00 и в прошлом уроке. Но у них есть дыры. Отладочная куча замечает испорченные защитные байты только при `delete`, то есть **поздно**. Проверки STL работают лишь для контейнеров, а не для `new int[4]` или встроенных массивов. И никто из них не ловит чтение за границей, только запись.

AddressSanitizer ловит **каждое** неверное обращение в момент, когда оно происходит, и показывает, где была выделена и где освобождена память.

## Подключаем AddressSanitizer

ASan включается флагом компилятора `/fsanitize=address`. Мы сделаем для него **отдельную сборку** в своей папке `build-asan`, чтобы обычная Debug-сборка оставалась быстрой.

**Шаг 1.** Добавь в главный `practice/CMakeLists.txt` блок перед строкой `# ---------- Движок ----------`:

```cmake
# ---------- AddressSanitizer (модуль 03) ----------
# Включается пресетом msvc-asan: cmake --preset msvc-asan
option(EMBER_ASAN "Собрать с AddressSanitizer" OFF)
if(MSVC AND EMBER_ASAN)
    add_compile_options(/fsanitize=address)
    add_link_options(/INCREMENTAL:NO)
    # ASan несовместим с проверками /RTC1, которые CMake добавляет в Debug
    string(REPLACE "/RTC1" "" CMAKE_CXX_FLAGS_DEBUG "${CMAKE_CXX_FLAGS_DEBUG}")
    # Программам с ASan нужна его библиотека (DLL) рядом с .exe
    get_filename_component(MSVC_BIN_DIR "${CMAKE_CXX_COMPILER}" DIRECTORY)
    foreach(config Debug Release RelWithDebInfo)
        file(COPY "${MSVC_BIN_DIR}/clang_rt.asan_dynamic-x86_64.dll"
                  "${MSVC_BIN_DIR}/clang_rt.asan_dbg_dynamic-x86_64.dll"
             DESTINATION "${CMAKE_BINARY_DIR}/bin/${config}")
    endforeach()
endif()
```

Что здесь происходит:
- `option(EMBER_ASAN ...)` объявляет **кэш-переменную** CMake со значением по умолчанию `OFF`. Её можно включить пресетом или командой `cmake -DEMBER_ASAN=ON`.
- `/fsanitize=address` — сам ASan. `/INCREMENTAL:NO` выключает инкрементальную линковку: с ASan она всё равно не работает, и без этой строки линковщик выдаёт предупреждение `LNK4300`.
- `/RTC1` и ASan несовместимы, поэтому мы вырезаем `/RTC1` из флагов Debug. `string(REPLACE ...)` — обычная замена подстроки в строке.
- ASan состоит из двух частей: проверки, которые компилятор вставляет в твой код, и **библиотека времени выполнения** (`clang_rt.asan_*.dll`). Visual Studio IDE сама подсказывает Windows, где её искать, а при запуске из VS Code программа её не найдёт. Поэтому мы копируем DLL из папки компилятора (`CMAKE_CXX_COMPILER` — полный путь к `cl.exe`) рядом с нашими `.exe`.

**Шаг 2.** В `practice/CMakePresets.json` добавь пресет конфигурации (в массив `configurePresets`) и пресет сборки (в `buildPresets`):

```json
{
  "name": "msvc-asan",
  "displayName": "MSVC x64 + AddressSanitizer",
  "inherits": "msvc",
  "binaryDir": "${sourceDir}/build-asan",
  "cacheVariables": { "EMBER_ASAN": "ON" }
}
```

```json
{ "name": "asan", "displayName": "Debug + ASan", "configurePreset": "msvc-asan", "configuration": "Debug" }
```

`"inherits": "msvc"` берёт у основного пресета генератор и архитектуру, а мы меняем папку сборки и включаем `EMBER_ASAN`.

**Шаг 3.** Добавь `build-asan/` в `.gitignore` и в `files.exclude` в `.vscode/settings.json` (рядом с `build`).

**Шаг 4.** В панели CMake (или `Ctrl+Shift+P` → **CMake: Select Configure Preset**) выбери **MSVC x64 + AddressSanitizer**, затем build-пресет **Debug + ASan**. Собирай и запускай как обычно. Чтобы вернуться к обычной сборке, выбери обратно пресет `MSVC x64 (Visual Studio 2026)`.

> [!tip] Командная строка
> ```powershell
> cmake --preset msvc-asan
> cmake --build --preset asan --target m03_overflow
> .\build-asan\bin\Debug\m03_overflow.exe
> ```

## Читаем отчёты

### Выход за границу кучи

```cpp
#include <print>

int main() {
    int* scores = new int[4]{10, 20, 30, 40};
    int sum = 0;
    for (int i = 0; i <= 4; ++i) {      // ошибка: <= вместо <
        sum += scores[i];
    }
    std::println("Сумма: {}", sum);
    delete[] scores;
}
```

В обычной Debug-сборке программа молча напечатает `Сумма: -33685919`. Откуда такое число? Сразу за блоком лежат защитные байты отладочной кучи `0xFDFDFDFD`, то есть −33 686 019, и вместе с честной суммой 100 получается ровно −33 685 919. Никакого сообщения об ошибке: только странный результат. С ASan программа останавливается в момент ошибки (пути сокращены):

```
==14660==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x11817b9a0040 ...
READ of size 4 at 0x11817b9a0040 thread T0
    #0 0x7ff679ba1451 in main ...\m03_memory\overflow.cpp:7
    #1 0x7ff679c83d98 in invoke_main ...
    ...
0x11817b9a0040 is located 0 bytes after 16-byte region [0x11817b9a0030,0x11817b9a0040)
allocated by thread T0 here:
    #0 0x7ff679c82a5e in operator new[] ...
    #1 0x7ff679ba111c in main ...\m03_memory\overflow.cpp:4

SUMMARY: AddressSanitizer: heap-buffer-overflow ...\overflow.cpp:7 in main
```

Как читать:
1. **Тип ошибки**: `heap-buffer-overflow` — выход за границу блока в куче.
2. **Что сделали**: `READ of size 4` — прочитали 4 байта (один `int`).
3. **Где**: стек вызовов, кадр `#0` — `overflow.cpp:7`, строка `sum += scores[i];`. Номера кадров идут от места ошибки к `main` и дальше в код запуска CRT.
4. **Относительно чего**: `0 bytes after 16-byte region` — сразу **за концом** 16-байтового блока (4 `int`). Классическая ошибка на единицу.
5. **Откуда блок**: `allocated by thread T0 here` — выделен в `overflow.cpp:4` через `operator new[]`.

> [!tip] Ищи первый кадр в своём коде
> Если ошибка случилась внутри функции стандартной библиотеки (например, ты передал висячую ссылку в `std::println`), то кадры `#0`, `#1`… будут указывать в недра STL с длинными шаблонными именами. Пролистай стек вниз до первого кадра с **твоим** файлом: ошибка почти всегда там.

### Обращение после освобождения

```cpp
#include <print>

struct Enemy {
    int health = 100;
};

int main() {
    Enemy* imp = new Enemy{60};
    delete imp;                    // враг убит, память освобождена
    int hp = imp->health;          // ...но указатель остался
    std::println("Здоровье: {}", hp);
}
```

```
==9656==ERROR: AddressSanitizer: heap-use-after-free on address 0x11e17b6a0030 ...
READ of size 4 at 0x11e17b6a0030 thread T0
    #0 0x7ff6d743121f in main ...\uaf.cpp:10
0x11e17b6a0030 is located 0 bytes inside of 4-byte region [0x11e17b6a0030,0x11e17b6a0034)
freed by thread T0 here:
    #0 0x7ff6d7512763 in operator delete ...
    #1 0x7ff6d74311bf in main ...\uaf.cpp:9
previously allocated by thread T0 here:
    #0 0x7ff6d7512645 in operator new ...
    #1 0x7ff6d74310ea in main ...\uaf.cpp:8
```

Три стека: **где** обратились к мёртвой памяти (строка 10), **где** её освободили (строка 9) и **где** выделили (строка 8). В реальном движке эти три места могут быть в трёх разных подсистемах, и без ASan связать их почти невозможно.

### Выход за границу на стеке и двойное удаление

```cpp
int scores[4] = {10, 20, 30, 40};
int index = 4;
int value = scores[index];     // ERROR: AddressSanitizer: stack-buffer-overflow
```

```cpp
Enemy* imp = new Enemy{};
delete imp;
delete imp;                    // ERROR: AddressSanitizer: attempting double-free
```

Для стекового массива ASan сообщает `stack-buffer-overflow` и перечисляет переменные кадра, рядом с которыми произошла ошибка. Для двойного удаления — `attempting double-free` и место первого `delete`.

## Как устроен ASan

> [!deep] Теневая память и красные зоны
> ASan заводит **теневую память** (shadow memory): на каждые 8 байт памяти программы — 1 байт тени, который хранит, сколько из этих 8 байт доступно. `00` — все восемь, `04` — первые четыре, особые значения — «запрещено» с указанием причины.
>
> Компилятор перед **каждым** чтением и записью памяти в твоём коде вставляет проверку: найти байт тени для адреса и убедиться, что доступ разрешён. Отсюда и замедление примерно в два раза.
>
> Аллокатор ASan окружает каждый блок в куче **красными зонами** (redzones): запрещёнными байтами, в тени помеченными `fa`. Выход за границу даже на один байт попадает в красную зону и сразу ловится. Освобождённые блоки помечаются `fd` и не возвращаются в оборот сразу, а какое-то время лежат в «карантине», чтобы use-after-free успел попасться. Локальные массивы на стеке тоже получают красные зоны по бокам.
>
> Ты видел всё это внизу отчёта: таблица `Shadow bytes around the buggy address` с `fa`, `fd` и `00`, а квадратные скобки `[fa]` отмечают байт тени для ошибочного адреса.

> [!warning] Чего ASan в MSVC не умеет
> - **Утечки памяти** не ищет (в Clang для этого есть LeakSanitizer, в MSVC его нет). Используй отчёт отладочной кучи CRT из [[03.4 Куча — new и delete#Утечки памяти|урока 03.4]].
> - **Чтение неинициализированной памяти** не ловит: это задача другого инструмента (MemorySanitizer), которого в MSVC нет. Тут помогают предупреждения и `/RTC1`.
> - **Несовпадение `new[]` и `delete`** по умолчанию не ловит.
> - **Не видит код, собранный без ASan**: библиотеки, которые не перекомпилированы с флагом.
> - **Гонки данных** между потоками — задача ThreadSanitizer (в модуле 14 обсудим, чем его заменить на Windows).

> [!engine] Санитайзеры в индустрии
> - В больших студиях есть ночные сборки движка с ASan: автоматические тесты гоняют игру по уровням, и любой отчёт санитайзера превращается в задачу в баг-трекере.
> - **Фаззинг**: программа скармливает загрузчикам ресурсов (текстур, моделей, уровней) миллионы случайно испорченных файлов, а ASan ловит каждое переполнение. Так находят уязвимости в форматах файлов, которые могут прийти от моддеров или из сети.
> - Chrome, Firefox, Unreal Engine регулярно прогоняются под санитайзерами.
>
> Для нас правило простое: **каждый практикум с указателями проверяй сборкой с ASan**.

> [!try] Попробуй сам
> 1. Подключи ASan по шагам урока. Собери пример с выходом за границу кучи в обычной Debug и в Debug + ASan и сравни поведение.
> 2. Повтори для use-after-free, стекового массива и двойного удаления.
> 3. Замени в примере с переполнением `new int[4]` на `std::vector<int>(4)` и `scores[i]` оставь как есть. Кто поймает ошибку в обычной Debug-сборке? А в сборке с ASan?

> [!quiz]- Проверь себя
> 1. Почему ошибки памяти так трудно найти обычным отладчиком?
> 2. Что делает строка `string(REPLACE "/RTC1" "" CMAKE_CXX_FLAGS_DEBUG ...)` и зачем она нужна?
> 3. Зачем копировать `clang_rt.asan_*.dll` рядом с `.exe`?
> 4. В отчёте ASan написано `0 bytes after 16-byte region`. Что это значит?
> 5. Какие три места показывает отчёт о use-after-free?
> 6. Почему ASan замедляет программу?
> 7. Чем искать утечки, если ASan в MSVC их не ловит?
>
> > [!success]- Ответы
> > 1. Ошибка проявляется не там, где совершена: испорченные данные читаются позже, в другом коде, и в момент падения отладчик показывает невиновное место.
> > 2. Удаляет флаг `/RTC1` из флагов Debug-конфигурации: он несовместим с AddressSanitizer.
> > 3. Это библиотека времени выполнения ASan. При запуске из VS Code Windows не знает, где её искать, а рядом с `.exe` она найдётся автоматически.
> > 4. Обращение сразу за концом 16-байтового блока: выход за границу на один элемент.
> > 5. Где произошло обращение к освобождённой памяти, где её освободили и где выделили.
> > 6. Перед каждым чтением и записью памяти выполняется проверка теневой памяти, а аллокатор добавляет красные зоны и держит освобождённые блоки в карантине.
> > 7. Отчётом отладочной кучи CRT (`_CrtSetDbgFlag` с `_CRTDBG_LEAK_CHECK_DF`).
