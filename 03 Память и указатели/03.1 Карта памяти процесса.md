# 03.1 Карта памяти процесса

## Адрес — это просто номер байта

Память компьютера можно представить как огромный массив байтов. У каждого байта есть **номер** — **адрес**. Переменная `int health` занимает 4 байта подряд, и её адрес — номер первого из них.

На x64 адрес — 64-битное число, его принято записывать в шестнадцатеричном виде: `0x000000d7ab4ff854`. Чтобы узнать адрес переменной, есть оператор `&` (подробно в [[03.2 Указатели|следующем уроке]]):

```cpp
int health = 100;
std::println("{}", static_cast<const void*>(&health));   // 0xd7ab4ff854 — где лежит health
```

`static_cast<const void*>` нужен, чтобы `std::println` напечатал адрес как адрес. Почему так, станет ясно в следующем уроке.

## Виртуальная память

Если запустить две копии одной программы, у переменной `health` в обеих может оказаться **одинаковый** адрес. При этом это разные переменные в разных местах оперативной памяти. Как такое возможно?

Адреса, с которыми работает программа, **виртуальные**. Каждый процесс получает своё собственное **адресное пространство**: на x64 Windows это 128 ТБ адресов только для пользовательского кода, гораздо больше, чем физической памяти в компьютере. Операционная система вместе с процессором (блоком управления памятью, **MMU**) переводит виртуальные адреса в физические **страницами** по 4 КБ:

```
Процесс A                    Физическая память (RAM)        Процесс B
виртуальные страницы                                          виртуальные страницы
┌─────────────┐              ┌─────────────┐              ┌─────────────┐
│ 0x...1000   │────────┐     │ страница 17 │     ┌────────│ 0x...1000   │
├─────────────┤        └────►├─────────────┤     │        ├─────────────┤
│ 0x...2000   │──────┐       │ страница 18 │◄────┘        │ 0x...2000   │──┐
├─────────────┤      │       ├─────────────┤              ├─────────────┤  │
│ не выделено │      └──────►│ страница 19 │              │ не выделено │  │  (выгружена
└─────────────┘              └─────────────┘              └─────────────┘  └─► в файл подкачки)
```

Что это даёт:
- **Изоляция.** Процесс не может испортить память другого процесса: у него просто нет адресов, которые туда ведут.
- **Защита.** У каждой страницы есть права: чтение, запись, выполнение. Нарушение прав — немедленное аварийное завершение.
- **Ленивость.** Страница получает физическую память только при первом обращении. Программа может «зарезервировать» гигабайты адресов, а занять реально лишь то, что использует.

> [!deep] Под капотом: таблицы страниц и TLB
> Перевод адресов хранится в **таблицах страниц** (page tables), которые операционная система ведёт для каждого процесса. Процессор при каждом обращении к памяти должен перевести адрес, и чтобы не читать таблицы каждый раз, он кэширует недавние переводы в **TLB** (Translation Lookaside Buffer). Промах TLB стоит десятки тактов. Это одна из причин, почему программа, которая прыгает по памяти хаотично (связные списки, разбросанные объекты), работает медленнее программы, которая идёт по памяти подряд. Мы вернёмся к этому в модуле 11.

## Области памяти процесса

Адресное пространство процесса поделено на области с разным назначением:

| Область | Что там лежит | Права | Время жизни |
|---|---|---|---|
| **Код** (`.text`) | Машинный код функций | чтение + выполнение | вся программа |
| **Константы** (`.rdata`) | Строковые литералы, `const`-данные, таблицы | только чтение | вся программа |
| **Данные** (`.data`, `.bss`) | Глобальные и `static`-переменные | чтение + запись | вся программа |
| **Куча** (heap) | Объекты, созданные через `new`, буферы `vector` и `string` | чтение + запись | пока не освободят |
| **Стек** (stack) | Кадры вызовов: локальные переменные, адреса возврата | чтение + запись | до выхода из функции |
| **DLL** | Код и данные подключённых библиотек | по-разному | вся программа |

Первые три области — это **образ программы**: секции из `.exe`-файла, которые загрузчик Windows отображает в память ([[00.2 Как исходник становится программой#Этап 4. Запуск|урок 00.2]]). Названия секций (`.text`, `.rdata`, `.data`) — те самые, что показывает `dumpbin`.

## Смотрим на настоящие адреса

```cpp
#include <print>
#include <vector>

int globalScore = 42;                  // глобальная переменная
const char* const title = "Ember";     // указатель на строковый литерал

void someFunction() {}

int main() {
    static int frameCounter = 0;       // статическая локальная
    int localHealth = 100;             // локальная (стек)
    std::vector<int> enemies(10);      // буфер вектора — в куче

    std::println("Код (someFunction):    {}", reinterpret_cast<const void*>(&someFunction));
    std::println("Строковый литерал:     {}", static_cast<const void*>(title));
    std::println("Глобальная переменная: {}", static_cast<const void*>(&globalScore));
    std::println("Статическая локальная: {}", static_cast<const void*>(&frameCounter));
    std::println("Куча (буфер vector):   {}", static_cast<const void*>(enemies.data()));
    std::println("Стек (localHealth):    {}", static_cast<const void*>(&localHealth));
}
```

Вот что напечатала эта программа у меня, запущенная **дважды подряд** (Debug):

| | Первый запуск | Второй запуск |
|---|---|---|
| Код | `0x7ff630fc14a6` | `0x7ff630fc14a6` |
| Строковый литерал | `0x7ff63109bb48` | `0x7ff63109bb48` |
| Глобальная переменная | `0x7ff6310dc000` | `0x7ff6310dc000` |
| Статическая локальная | `0x7ff6310dc9d4` | `0x7ff6310dc9d4` |
| Куча | `0x201a4c4afd0` | `0x2506be7a6f0` |
| Стек | `0x35c12ff604` | `0x8109d0f7f4` |

Научимся это читать:

1. **Код, литерал, глобальные и статические переменные** лежат рядом, в районе `0x7ff6…`: это образ программы, загруженный из `.exe`. Порядок внутри него — как секции файла: сначала код (`.text`), потом константы (`.rdata`), потом изменяемые данные (`.data`).
2. **Статическая локальная** `frameCounter` лежит рядом с глобальной `globalScore`. Видимость у неё локальная, но живёт она в той же области, что и глобальные переменные ([[02.4 Области видимости, время жизни и пространства имён#static внутри функции|урок 02.4]]).
3. **Куча и стек** находятся в совсем других местах и **меняются от запуска к запуску**.
4. Образ программы **не сменил адрес** между запусками, а куча и стек сменили.

> [!deep] ASLR: почему адреса случайные
> Windows специально размещает области памяти по случайным адресам: это **ASLR** (Address Space Layout Randomization). Если злоумышленник нашёл ошибку переполнения буфера, ему нужно знать, куда прыгнуть, а случайные адреса сильно затрудняют атаку.
>
> Адрес образа программы Windows выбирает **один раз при загрузке системы** и сохраняет для всех запусков этого `.exe` (так он может делить страницы кода между копиями программы). Поэтому в нашей таблице код не сдвинулся. А стек и куча перемешиваются при каждом запуске. После перезагрузки компьютера сменятся и адреса образа.
>
> Следствие для отладки: **не запоминай адреса** между запусками. Адрес `0x2506be7a6f0` в логе вчерашнего запуска ничего не скажет о сегодняшнем.

## Стек растёт вниз

В [[02.2 Как работает вызов — стек и рекурсия#Стек вызовов|уроке 02.2]] мы говорили, что стек растёт в сторону меньших адресов. Проверим:

```cpp
#include <cstdint>
#include <print>

void dive(int depth) {
    int local = depth;
    auto address = reinterpret_cast<std::uintptr_t>(&local);
    std::println("Глубина {}: адрес local = {:#x}", depth, address);
    if (depth < 4) {
        dive(depth + 1);
    }
}

int main() {
    dive(1);
}
```

```
Глубина 1: адрес local = 0xd7ab4ff854
Глубина 2: адрес local = 0xd7ab4ff7b4
Глубина 3: адрес local = 0xd7ab4ff714
Глубина 4: адрес local = 0xd7ab4ff674
```

Каждый следующий вызов кладёт свой кадр **ниже** предыдущего, и адреса уменьшаются. Разница между соседними адресами — `0xA0` = 160 байт: это размер кадра функции `dive` в Debug-сборке. (`std::uintptr_t` из `<cstdint>` — целое число, в которое гарантированно помещается адрес; так его можно напечатать в нужном формате и вычитать.)

## Защита страниц и нулевой указатель

Каждая страница памяти имеет права доступа. Если программа их нарушает, процессор генерирует исключение, а Windows завершает процесс с кодом **`0xC0000005` — Access Violation** («нарушение прав доступа»). Ты увидишь этот код много раз. Типичные причины:

- **Обращение по адресу 0.** Самая первая страница адресного пространства специально **не отображена ни на что**. Указатель, который «никуда не указывает», равен нулю (`nullptr`), и обращение через него гарантированно падает, а не портит чужие данные тихо:
  ```cpp
  int* p = nullptr;
  std::println("{}", *p);   // Access violation reading location 0x0000000000000000
  ```
- **Запись в константы.** Строковые литералы лежат в `.rdata` с правом «только чтение». Попытка их изменить (через хитрые преобразования типов) обрывает программу.
- **Обращение к неотображённой памяти**: давно освобождённой или просто случайному адресу из мусорного указателя.

> [!warning] Не все ошибки падают
> Защита страниц работает с точностью до **страницы** (4 КБ). Если программа вышла за границу своего массива на пару байт, она почти наверняка попадёт в соседние данные **той же** страницы, и никакого исключения не будет: просто тихо испортятся чужие переменные. Падение `0xC0000005` — это ещё удачный исход. Для ловли тихих ошибок есть инструменты, о них в [[03.5 Неопределённое поведение и AddressSanitizer|уроке 03.5]].

## Откуда программа берёт память

- **Стек** выделяется при создании потока: Windows **резервирует** 1 МБ адресов, но физическую память отдаёт постранично, по мере того как стек растёт. Ниже последней страницы стоит **защитная страница** (guard page): обращение к ней значит «стек кончился», отсюда исключение `0xC00000FD` из [[02.2 Как работает вызов — стек и рекурсия#Переполнение стека|урока 02.2]].
- **Куча** управляется библиотекой времени выполнения поверх кучи Windows. Когда ей не хватает места, она просит у ОС новые страницы функцией WinAPI `VirtualAlloc`. Подробно в [[03.4 Куча — new и delete|уроке 03.4]].

В Диспетчере задач на вкладке «Подробности» можно посмотреть, сколько памяти занимает процесс. Колонка «Рабочий набор» показывает страницы, которые сейчас реально находятся в физической памяти.

> [!engine] Память в движках
> - **Бюджеты памяти.** У консолей фиксированный объём памяти и нет файла подкачки. Поэтому движки делят память на бюджеты: столько-то мегабайт текстурам, столько-то звуку, столько-то логике, и следят за ними в реальном времени. Превысил бюджет — игра упадёт на консоли, даже если на ПК всё работало.
> - **Резервирование адресов.** Движок может зарезервировать, например, 64 ГБ адресного пространства одним вызовом `VirtualAlloc` и потом подключать к нему физические страницы по мере надобности. Получается растущий массив, который **никогда не переезжает**, и ссылки на его элементы не висят. Этот приём мы используем в аллокаторах модуля 12.
> - **Страницы-ловушки.** Отладочные аллокаторы (в Unreal он называется *stomp allocator*) кладут каждый объект в конец отдельной страницы, а следующую страницу помечают недоступной. Выход за границу объекта хотя бы на байт тут же вызывает `0xC0000005` точно в месте ошибки. Медленно и прожорливо, но спасает при охоте на порчу памяти.

> [!compare] А как в C#, Go и Python?
> Под капотом всё то же самое: те же страницы, стек и куча, ведь это механизмы ОС и процессора. Разница в том, что **кучей управляет среда выполнения**: сборщик мусора сам решает, где разместить объект, когда его освободить и даже когда **переместить** (сборщик .NET уплотняет кучу, сдвигая объекты). Поэтому в C# адрес объекта не постоянен, и получить его можно только в блоке `fixed`. В C++ объект лежит там, где его создали, до самого уничтожения.

> 2. Добавь в программу второй вектор и большой локальный массив `std::array<int, 1000>`. Где они оказались?
> 3. Запусти `dive` в Release. Изменился ли размер кадра? Почему?

> [!quiz]- Проверь себя
> 1. Почему у одной и той же переменной в двух одновременно запущенных копиях программы может быть одинаковый адрес?
> 2. Назови области памяти процесса и что лежит в каждой.
> 3. Где лежит `static`-переменная внутри функции?
> 4. Почему обращение через `nullptr` падает, а выход за границу массива на пару байт обычно нет?
> 5. Что означает код завершения `0xC0000005`?
> 6. Почему адреса кучи меняются от запуска к запуску?
>
> > [!success]- Ответы
> > 1. Адреса виртуальные: у каждого процесса своё адресное пространство, и ОС отображает одинаковые виртуальные адреса разных процессов на разные физические страницы.
> > 2. Код (`.text`): машинные инструкции. Константы (`.rdata`): литералы, константные данные. Данные (`.data`/`.bss`): глобальные и статические переменные. Куча: динамически выделенные объекты. Стек: кадры вызовов. Плюс DLL.
> > 3. В области глобальных данных (`.data`/`.bss`), рядом с глобальными переменными.
> > 4. Нулевая страница специально не отображена, поэтому любое обращение к ней вызывает исключение. Защита работает постранично, а соседние байты массива обычно лежат в той же, доступной странице.
> > 5. Access Violation: программа обратилась к памяти, на которую у неё нет прав (неотображённая страница, запись в страницу «только для чтения» и т.п.).
> > 6. Из-за ASLR: Windows размещает кучу и стек по случайным адресам при каждом запуске, чтобы затруднить атаки.
