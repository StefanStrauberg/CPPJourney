# 00.6 Отладчик — главный инструмент

> [!abstract] О чём урок
> - точки останова, пошаговое выполнение, просмотр переменных и стека вызовов;
> - условные точки останова и точки журнала (logpoints);
> - как отладчик работает «под капотом»: инструкция `int 3` и файлы `.pdb`;
> - «магические числа» MSVC (`0xCCCCCCCC` и компания), по которым опытные программисты узнают баги с первого взгляда.
>
> Синтаксис программы в этом уроке ещё не разобран, но он похож на C#, Go и Java, и ты его поймёшь. Сосредоточься на **инструменте**.

## Зачем отладчик, если есть `println`

Отладка печатью (`println` в подозрительных местах) работает, но медленно: добавил вывод, пересобрал, запустил, посмотрел, добавил ещё. Отладчик позволяет **остановить программу в любой точке** и посмотреть на всё сразу: значения всех переменных, цепочку вызовов функций, содержимое памяти. И менять значения на лету.

> [!engine] Программисты движков живут в отладчике
> Большая часть работы над движком — не написание нового кода, а поиск причин, почему старый ведёт себя странно: объект проваливается сквозь пол на 3000-м кадре, текстура портится только на одной карте, игра падает раз в час. Без уверенного владения отладчиком такие баги не найти. Чем раньше отладчик станет привычкой, тем лучше.

## Подопытная программа

Создай `m00_setup/debug_demo.cpp` и добавь цель `m00_debug_demo` в `m00_setup/CMakeLists.txt` (как в [[00.5 Проект курса в VS Code#Шаг 9. Как добавить новую программу|шаге 9 прошлого урока]]):

```cpp
#include <print>

// Урон выстрела на заданном расстоянии:
// чем дальше цель, тем меньше урон, но не меньше minDamage.
int damageAtDistance(int baseDamage, int distance) {
    const int minDamage = 5;
    int damage = baseDamage - distance * 2;
    if (damage < minDamage) {
        damage = minDamage;
    }
    return damage;
}

int main() {
    int totalDamage = 0;

    // Игрок стреляет по пяти врагам на расстоянии 0, 10, 20, 30, 40
    for (int distance = 0; distance <= 40; distance += 10) {
        int damage = damageAtDistance(30, distance);
        totalDamage += damage;
        std::println("Расстояние {:2} -> урон {}", distance, damage);
    }

    std::println("Суммарный урон: {}", totalDamage);
}
```

Запусти без отладки (`Ctrl+Shift+F5`, цель `m00_debug_demo`) и посмотри на вывод:

```
Расстояние  0 -> урон 30
Расстояние 10 -> урон 10
Расстояние 20 -> урон 5
Расстояние 30 -> урон 5
Расстояние 40 -> урон 5
Суммарный урон: 55
```

> [!warning] Отладка — только в Debug
> Убедись, что выбран build-пресет **Debug**. В Release компилятор переставляет и выбрасывает код, и отладчик будет показывать странные вещи (об этом ниже).

## Точка останова

**Точка останова** (breakpoint) — место, где программа остановится, когда выполнение до него дойдёт.

1. Щёлкни левее номера строки `int damage = damageAtDistance(30, distance);` или поставь курсор на строку и нажми **`F9`**. Появится красный кружок.
2. Нажми **`F5`**. Программа запустится и **остановится** на этой строке, а строка подсветится жёлтым.

> [!note] Жёлтая строка ещё не выполнена
> Подсвеченная строка — та, которая **будет** выполнена следующей. Переменная `damage` в ней пока не получила значения.

Что ты видишь слева, в панели **Run and Debug**:

| Панель | Что показывает |
|---|---|
| **Variables** → *Locals* | Все локальные переменные текущей функции: `totalDamage`, `distance`, `damage` |
| **Watch** | Выражения, за которыми ты следишь (добавляются кнопкой **+**) |
| **Call Stack** | Цепочка вызовов: какая функция вызвала текущую |
| **Breakpoints** | Список всех точек останова |

> [!try] Странное значение `damage`
> Посмотри на значение `damage` в панели Variables **до** выполнения строки. Скорее всего, там `-858993460` или другое странное число. Запомни его: ниже мы узнаем, откуда оно.

## Пошаговое выполнение

Вверху появилась панель отладки. Её кнопки и клавиши:

| Клавиша | Действие | Когда использовать |
|---|---|---|
| **`F5`** | Continue: выполнять до следующей точки останова | Перепрыгнуть к следующему интересному месту |
| **`F10`** | Step Over: выполнить текущую строку целиком | Функция в строке нас не интересует |
| **`F11`** | Step Into: зайти внутрь вызываемой функции | Хотим посмотреть, что функция делает |
| **`Shift+F11`** | Step Out: выполнить функцию до конца и вернуться | Зашли не туда, хотим обратно |
| **`Ctrl+Shift+F5`** | Restart: перезапустить программу | |
| **`Shift+F5`** | Stop: остановить отладку | |

Попробуй по шагам:

1. Ты стоишь на строке с `damageAtDistance`. Нажми **`F11`** — окажешься внутри функции `damageAtDistance`. В Variables теперь её переменные: `baseDamage = 30`, `distance = 0`.
2. Посмотри на **Call Stack**: вверху `damageAtDistance`, под ней `main`. Это стек вызовов: `main` вызвала `damageAtDistance`. Щёлкни по `main` в Call Stack, и редактор покажет место вызова и переменные `main`. Щёлкни обратно на `damageAtDistance`.
3. Нажимай **`F10`** и наблюдай, как меняется `damage`.
4. Дойдя до `return`, нажми `F10` ещё раз или **`Shift+F11`**: вернёшься в `main`. Нажми `F10`, и `damage` в `main` получит значение `30`.
5. Нажми **`F5`**. Цикл сделает круг и снова остановится на точке останова, но уже с `distance = 10`.

> [!warning] Не заходи в `std::println` по F11
> Если нажать `F11` на строке с `std::println`, отладчик честно зайдёт внутрь стандартной библиотеки, в сотни строк чужого шаблонного кода. Ничего страшного: нажми **`Shift+F11`** несколько раз, пока не вернёшься в свой код. На строках с библиотечными вызовами пользуйся `F10`.

## Наведение, Watch и Debug Console

- **Наведи мышь** на любую переменную в коде во время остановки, и появится её значение.
- В панели **Watch** нажми **+** и введи выражение, например `totalDamage * 2` или `distance > 15`. Оно будет пересчитываться на каждом шаге.
- Внизу есть вкладка **Debug Console**. В ней можно вычислить любое выражение: набери `baseDamage - distance` и нажми Enter.

### Изменение значений на лету

В панели Variables сделай двойной щелчок по значению переменной, например `distance`, и введи `100`. Программа продолжит работать с новым значением. Так проверяют гипотезы («а что будет, если расстояние огромное?»), не меняя код и не пересобирая.

## Условные точки останова и точки журнала

Представь, что цикл выполняется 10 000 раз, а ошибка проявляется только при `distance == 30`. Нажимать `F5` 3000 раз не хочется.

**Условная точка останова:**
1. Щёлкни правой кнопкой по красному кружку → **Edit Breakpoint…**
2. Выбери **Expression** и введи `distance == 30`, нажми Enter.
3. Кружок получит значок `=`. Перезапусти отладку: программа остановится, только когда условие истинно.

Там же есть вариант **Hit Count**: остановиться, например, на 4-м срабатывании.

**Точка журнала** (logpoint) — точка, которая не останавливает программу, а печатает сообщение в Debug Console:
1. Правый клик слева от номера строки → **Add Logpoint…**
2. Введи `distance = {distance}, total = {totalDamage}`. Выражения в фигурных скобках вычисляются.
3. Кружок станет ромбиком. Запусти отладку: сообщения появятся в Debug Console, а программа не остановится.

Logpoint — это «`println` без пересборки». Очень удобно, когда пересборка большого проекта занимает минуты.

## Под капотом

> [!deep] Как работает точка останова
> Отладчик — отдельная программа, которая управляет твоей через специальный интерфейс операционной системы (Debug API в Windows).
>
> Когда ты ставишь точку останова, отладчик **записывает поверх первого байта машинной инструкции** байт `0xCC`. Это инструкция `int 3`, «прерывание для отладчика». Процессор доходит до неё и генерирует исключение. Windows видит, что к процессу подключён отладчик, и **замораживает** процесс, сообщая отладчику: «остановились по такому-то адресу». Отладчик возвращает настоящий байт на место и показывает тебе состояние. При продолжении он выполняет одну оригинальную инструкцию, снова ставит `0xCC` и отпускает процесс.
>
> Ту же инструкцию можно вставить в код самому:
> ```cpp
> __debugbreak();   // встроенная функция MSVC: компилируется в int 3
> ```
> Если программа запущена под отладчиком, она остановится на этой строке. Если без отладчика, Windows сообщит о необработанном исключении. Движки используют `__debugbreak()` в своих **ассертах**: при нарушении условия программист сразу оказывается в отладчике в нужной точке. Такую систему мы напишем в модуле 09.

> [!deep] Как отладчик знает имена переменных: файлы `.pdb`
> В машинном коде нет ни имён переменных, ни номеров строк, только адреса и регистры. Связь между машинным кодом и исходником хранится в отдельном файле **`.pdb`** (Program Database), который линковщик создаёт рядом с `.exe` в Debug-сборке. В нём записано:
> - какой диапазон адресов соответствует какой строке какого файла;
> - где в памяти (смещение от начала кадра стека или регистр) лежит каждая переменная и какой у неё тип.
>
> Без `.pdb` отладчик покажет только ассемблер. Поэтому игровые студии хранят `.pdb` от **каждой** выпущенной версии игры: когда приходит отчёт о падении от игрока, по `.pdb` восстанавливают, в какой строке какой функции оно случилось.

> [!deep] Почему в Release отладчик «врёт»
> Попробуй переключиться на Release, поставить ту же точку останова и запустить `F5`. Ты увидишь, что:
> - некоторые переменные показаны как *optimized away* или с явно неверными значениями: компилятор держит их в регистрах или вообще выбросил;
> - пошаговое выполнение прыгает по строкам в странном порядке;
> - внутрь `damageAtDistance` не зайти: компилятор **встроил** её код прямо в `main`.
>
> Это не ошибка отладчика: оптимизированный код просто больше не соответствует исходнику строка в строку. Для отладки оптимизированного кода есть конфигурация `RelWithDebInfo`, но и с ней картинка неидеальная.

## Магические числа MSVC

Помнишь странное значение `-858993460` у ещё не инициализированной `damage`? Переведи его в шестнадцатеричную систему: это **`0xCCCCCCCC`**.

В Debug-сборке MSVC специально заполняет память узнаваемыми значениями, чтобы ошибки было видно сразу:

| Значение | Где появляется | Что означает |
|---|---|---|
| `0xCCCCCCCC` | Стек (локальные переменные) | Переменная **не инициализирована**. Флаг `/RTC1` заполняет кадр стека байтами `0xCC`. |
| `0xCDCDCDCD` | Куча | Память **выделена**, но в неё ничего не записали. |
| `0xDDDDDDDD` | Куча | Память **уже освобождена**. Обращение к ней — ошибка use-after-free. |
| `0xFDFDFDFD` | Куча, по краям блока | «Ничейная земля» (no man's land): защитные байты вокруг выделенного блока. Если они испорчены, значит, кто-то **вышел за границу** массива. |

Почему `0xCC`? Это та же инструкция `int 3`. Если программа по ошибке начнёт **выполнять** неинициализированную память стека как код, она тут же остановится в отладчике.

> [!engine] Узнавай баги по числам
> Увидел в отладчике указатель `0xDDDDDDDDDDDDDDDD`? Объект уже удалён, а кто-то продолжает им пользоваться. Значение здоровья игрока `-842150451` (это `0xCDCDCDCD`)? Объект создан в куче, но поле забыли инициализировать. Опытный программист движков ставит такие диагнозы за секунду. Мы ещё встретимся с этими значениями в модуле 03, когда начнём работать с памятью напрямую.

> [!try] Попробуй сам
> 1. Поставь точку останова на строку `return damage;` с условием `damage == 5`. Сколько раз она сработает за программу?
> 2. Во время остановки внутри `damageAtDistance` измени `baseDamage` на `100` через панель Variables. Как изменится вывод программы?
> 3. Добавь в начало `main` строку `__debugbreak();` и запусти: сначала с отладкой (`F5`), потом без (`Ctrl+Shift+F5`). Что произошло во втором случае? Не забудь потом убрать строку.

> [!quiz]- Проверь себя
> 1. Чем отличаются `F10` и `F11`?
> 2. Ты зашёл по `F11` внутрь стандартной библиотеки. Как быстро вернуться?
> 3. Цикл выполняется миллион раз, баг проявляется на итерации 765 432. Как остановиться именно там?
> 4. Что физически делает отладчик, когда ставит точку останова?
> 5. Зачем игровые студии хранят `.pdb` файлы всех выпущенных версий?
> 6. В отладчике у переменной `int ammo` значение `-858993460`. Какой диагноз?
>
> > [!success]- Ответы
> > 1. `F10` выполняет строку целиком, не заходя в функции. `F11` заходит внутрь вызываемой функции.
> > 2. `Shift+F11` (Step Out), при необходимости несколько раз.
> > 3. Условная точка останова с выражением на номер итерации или Hit Count = 765432.
> > 4. Записывает поверх инструкции байт `0xCC` (`int 3`). Процессор, дойдя до него, генерирует исключение, ОС замораживает процесс и отдаёт управление отладчику.
> > 5. Чтобы по адресам из отчётов о падениях у игроков восстанавливать функции и строки кода.
> > 6. `-858993460` = `0xCCCCCCCC`: переменная не инициализирована (стек заполнен `0xCC` в Debug-сборке).
