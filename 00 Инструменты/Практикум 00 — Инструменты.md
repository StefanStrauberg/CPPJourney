## Задание 1. Hello, Ember ⭐

> [!task] Условие
> Наш будущий движок называется **Ember** («тлеющий уголь»). Напиши программу `m00_banner`, которая выводит заставку движка: название, нарисованное символами (ASCII-art), версию и строку «Загрузка…».
>
> Затем:
> 1. Собери её в **Debug** и в **Release**.
> 2. Найди оба `.exe` в проводнике (папки `practice\build\bin\Debug` и `practice\build\bin\Release`) и сравни их размеры.
> 3. Запусти Release-версию двойным щелчком из проводника. Что произошло и почему?
>
> Пример заставки (придумай свою!):
> ```
>  _____ __  __ ____  _____ ____
> | ____|  \/  | __ )| ____|  _ \
> |  _| | |\/| |  _ \|  _| | |_) |
> | |___| |  | | |_) | |___|  _ <
> |_____|_|  |_|____/|_____|_| \_\
>        engine v0.0.1
> Загрузка...
> ```

> [!hint]- Подсказка
> Каждая строка — отдельный вызов `std::println("...");`. Если в рисунке есть обратная косая черта `\`, её нужно **удвоить**: `\\`. Внутри строки C++ одиночный `\` начинает специальную последовательность (как `\n` — перевод строки), точно как в C# и Go.
>
> Есть способ проще: **сырые строки** (raw string literals). Всё между `R"(` и `)"` берётся буквально, вместе с переводами строк и обратными чертами:
> ```cpp
> std::println(R"(
>  ____
> |  _ \
> )");
> ```
> В C# это аналог `@"..."`, в Go — строки в обратных кавычках.
>
> И ещё одна ловушка: для `std::println` фигурные скобки `{` и `}` особые, это места для подстановки значений. Если они нужны в рисунке как обычные символы, удваивай их: `{{` и `}}`.

> [!solution]- Решение
> `m00_setup/CMakeLists.txt` — добавь строку:
> ```cmake
> add_executable(m00_banner banner.cpp)
> ```
>
> `m00_setup/banner.cpp`:
> ```cpp
> #include <print>
>
> int main() {
>     std::println(R"(
>  _____ __  __ ____  _____ ____
> | ____|  \/  | __ )| ____|  _ \
> |  _| | |\/| |  _ \|  _| | |_) |
> | |___| |  | | |_) | |___|  _ <
> |_____|_|  |_|____/|_____|_| \_\
>        engine v0.0.1)");
>     std::println("Загрузка...");
> }
> ```
>
> **Размеры.** Debug-версия весит около мегабайта, Release — в несколько раз меньше. Причины: в Debug нет оптимизаций (код длиннее), добавлены проверки (`/RTC1`), а функции стандартной библиотеки не встроены, поэтому попадают в `.exe` целиком. Рядом с Debug-версией лежит ещё и `.pdb` на несколько мегабайт: отладочная информация.
>
> **Запуск из проводника.** Окно консоли мелькнёт и сразу закроется. Программа отработала за миллисекунды, и Windows закрыла консоль, созданную специально для неё. Во встроенном терминале VS Code такого нет: терминал живёт отдельно от программы. Если очень нужно запускать из проводника, можно в конце `main` ждать нажатия Enter (научимся в модуле 01).

## Задание 2. Сломай сборку ⭐

> [!task] Условие
> Лучший способ не бояться ошибок — устроить их самому. Создай программу `m00_broken` с таким кодом:
> ```cpp
> #include <print>
>
> int main() {
>     int hp = 100;
>     std::println("Здоровье: {}", hp);
> }
> ```
> Убедись, что она работает. Затем по очереди внеси **каждую** из поломок ниже (по одной, исправляя предыдущую!), нажми `F7` и для каждой запиши:
> - на каком **этапе** возникла ошибка (препроцессор, компилятор, линковщик, выполнение);
> - **код** ошибки и что он значит своими словами.
>
> 1. Опечатка в заголовке: `#include <prnt>`.
> 2. Неверный тип: `int hp = "сто";`.
> 3. Пропущенная точка с запятой после `std::println(...)`.
> 4. Функция без тела. Добавь **перед** `main` строку `int computeDamage(int level);`, а в `main` — `std::println("Урон: {}", computeDamage(3));`.
> 5. Выход за границу массива во время работы. Замени тело `main` на:
>    ```cpp
>    std::vector<int> ammo = {30, 8, 50};   // патроны: автомат, дробовик, пулемёт
>    std::println("Патронов в слоте 10: {}", ammo[10]);
>    ```
>    и добавь `#include <vector>` в начало файла. Запусти в **Debug**, а затем в **Release**.

> [!hint]- Подсказка
> Вспомни таблицу из [[00.2 Как исходник становится программой#Этап 3. Линковщик|урока 00.2]]: коды на **C** — компилятор (есть файл и строка), на **LNK** — линковщик (строки нет). Ошибка «не удаётся открыть файл включения» формально выдаётся компилятором, но случается на шаге препроцессора.

> [!solution]- Решение
> **1. `#include <prnt>`** — препроцессор:
> ```
> fatal error C1083: Не удается открыть файл включение: prnt: No such file or directory
> ```
> Препроцессор не нашёл файл, который нужно вставить. `fatal` означает, что компиляция прервана сразу.
>
> **2. `int hp = "сто";`** — компилятор (семантический анализ):
> ```
> error C2440: инициализация: невозможно преобразовать "const char [7]" в "int"
> ```
> Строковый литерал нельзя превратить в число. Обрати внимание на тип `const char [7]`: массив из 7 символов. В слове «сто» 3 буквы, каждая кириллическая буква в UTF-8 занимает 2 байта (6 байт) плюс невидимый нулевой байт в конце строки. В C++ размер строки считается в **байтах**, а не в буквах. Мы вернёмся к этому в модуле 01.
>
> **3. Пропущенная `;`** — компилятор (синтаксический анализ):
> ```
> error C2143: синтаксическая ошибка: отсутствие ";" перед "}"
> ```
> Компилятор заметил проблему только на следующей лексеме, `}`. Поэтому ошибка «о точке с запятой» часто указывает на строку **после** настоящего места ошибки.
>
> **4. Функция без тела** — линковщик:
> ```
> error LNK2019: ссылка на неразрешенный внешний символ "int __cdecl computeDamage(int)" (?computeDamage@@YAHH@Z) в функции main
> fatal error LNK1120: неразрешенных внешних элементов: 1
> ```
> Компилятор поверил **объявлению** и сгенерировал вызов. Линковщик стал искать **определение** символа `?computeDamage@@YAHH@Z` во всех `.obj` и библиотеках и не нашёл. Видишь декорированное имя из урока 00.2?
>
> **5. Выход за границу** — во время выполнения:
> - **Debug**: появляется окно *Debug Assertion Failed!* с текстом `vector subscript out of range`. Отладочная версия стандартной библиотеки MSVC проверяет индексы и ловит ошибку. Если нажать **Retry** при запущенном отладчике, он остановится прямо в месте ошибки.
> - **Release**: программа, скорее всего, **напечатает какое-то число** и спокойно завершится. Проверок нет, и программа прочитала чужую память за концом массива. Это **неопределённое поведение**: в другой раз может напечатать другое число или упасть.
>
> Вывод: Debug-сборка — твоя страховочная сетка. Разрабатывай и тестируй в Debug.

## Задание 3. Детектив — потерянный уровень ⭐⭐

> [!task] Условие
> Программа считает, какого уровня достигнет игрок, накопив 1000 очков опыта. Для перехода с 1-го уровня на 2-й нужно 100 опыта, со 2-го на 3-й — 200, с 3-го на 4-й — 300 и так далее (каждый уровень дороже предыдущего на 100).
>
> ```cpp
> #include <print>
>
> int main() {
>     int xp = 1000;     // накопленный опыт
>     int level = 1;     // текущий уровень
>     int cost = 100;    // сколько опыта нужно до следующего уровня
>
>     while (xp > cost) {
>         xp -= cost;    // тратим опыт на уровень
>         level += 1;
>         cost += 100;   // следующий уровень дороже
>     }
>
>     std::println("Уровень: {}, остаток опыта: {}", level, xp);
> }
> ```
>
> Программа печатает `Уровень: 4, остаток опыта: 400`. Посчитай на бумаге, каким должен быть правильный ответ. Затем найди ошибку **с помощью отладчика**, не добавляя в код никаких `println`. Используй точку останова внутри цикла и панель Variables или Watch. Исправь ошибку.

> [!hint]- Подсказка
> Поставь точку останова на строку `xp -= cost;` и нажимай `F5`, следя за `xp` и `cost`. Что происходит, когда опыта осталось **ровно** столько, сколько нужно? Можно добавить в Watch выражение `xp > cost` и посмотреть его значение на последней итерации.

> [!solution]- Решение
> Правильный ответ: **уровень 5, остаток 0**. 100 + 200 + 300 + 400 = 1000, опыта хватает ровно.
>
> В отладчике видно: после трёх итераций `xp = 400`, `cost = 400`. Условие `xp > cost` (400 > 400) ложно, и цикл заканчивается, хотя опыта хватает. Ошибка в сравнении: нужно «больше **или равно**».
> ```cpp
> while (xp >= cost) {
> ```
> Это классическая **ошибка на единицу** (off-by-one): граничный случай обработан неправильно. Такие ошибки — самые частые в программировании, и почти всегда они прячутся в условиях циклов и сравнениях `<` против `<=`.

## Задание 4. Детектив — волны врагов ⭐⭐

> [!task] Условие
> Программа считает, сколько всего врагов придёт за три волны (10, 20 и 30):
> ```cpp
> #include <print>
>
> int main() {
>     int total;
>     for (int wave = 1; wave <= 3; ++wave) {
>         total += wave * 10;
>     }
>     std::println("Всего врагов: {}", total);
> }
> ```
> 1. Собери её в **Debug** и посмотри в панель **Problems**: что говорит компилятор?
> 2. Запусти в Debug через отладчик (`F5`). Что произошло?
> 3. Запусти в **Release** (`Ctrl+Shift+F5`). Что напечаталось?
> 4. Объясни, почему результаты разные, и исправь программу.

> [!hint]- Подсказка
> Каким значением начинается `total`? Вспомни раздел [[00.6 Отладчик — главный инструмент#Магические числа MSVC|«Магические числа MSVC»]].

> [!solution]- Решение
> 1. Компилятор предупреждает:
>    ```
>    warning C4700: использована неинициализированная локальная переменная "total"
>    ```
>    Предупреждение, а не ошибка, поэтому сборка проходит. Но это **прямое указание на баг**.
> 2. В Debug отладчик останавливается с сообщением *Run-Time Check Failure #3 — The variable 'total' is being used without being initialized*. Это работает проверка `/RTC1`. Без отладчика программа аварийно завершается.
> 3. В Release программа, скорее всего, напечатает `Всего врагов: 60`. **Правильный ответ, хотя программа неправильная!** Чтение неинициализированной переменной — неопределённое поведение, и в этот раз оно случайно «сработало». С другой версией компилятора, другими флагами или после небольшой правки соседнего кода может напечатать что угодно.
> 4. Переменную нужно инициализировать:
>    ```cpp
>    int total = 0;
>    ```
>
> **Мораль:**
> - предупреждения компилятора нужно читать и исправлять **все**; в серьёзных проектах включают флаг `/WX`, превращающий предупреждения в ошибки;
> - то, что программа в Release выдала правильный ответ, **ничего не доказывает**;
> - всегда инициализируй переменные при объявлении.

## Задание 5. Release-сюрприз ⭐⭐

> [!task] Условие
> Добавь программу `m00_speed` с кодом ниже. Это «симуляция» 10 миллионов частиц на 10 кадров: каждая частица сдвигается на `скорость × время кадра`. Синтаксис пока не важен.
> ```cpp
> #include <chrono>
> #include <print>
> #include <vector>
>
> int main() {
>     // 10 миллионов «частиц» с координатой и скоростью
>     const int count = 10'000'000;
>     std::vector<float> x(count, 0.0f);
>     std::vector<float> v(count, 1.5f);
>
>     auto start = std::chrono::steady_clock::now();
>
>     // 10 «кадров» симуляции: x += v * dt
>     const float dt = 1.0f / 60.0f;
>     for (int frame = 0; frame < 10; ++frame) {
>         for (int i = 0; i < count; ++i) {
>             x[i] += v[i] * dt;
>         }
>     }
>
>     auto finish = std::chrono::steady_clock::now();
>     auto ms = std::chrono::duration<double, std::milli>(finish - start).count();
>
>     std::println("10 кадров по {} частиц: {:.1f} мс", count, ms);
>     std::println("Контроль: x[123] = {:.3f}", x[123]);
> }
> ```
> 1. Запусти в Debug и в Release, каждую по 2–3 раза. Запиши время.
> 2. Во сколько раз Release быстрее?
> 3. Сколько миллисекунд уходит на **один** кадр в каждой конфигурации? Уложились бы мы в бюджет кадра 16,7 мс (60 FPS)?
> 4. Сколько частиц можно обновлять каждый кадр в Release, если на эту работу выделено 2 мс из бюджета кадра?

> [!hint]- Подсказка
> Время одного кадра = общее время / 10. Для пункта 4: узнай, сколько частиц обновляется за 1 мс в Release, и умножь на 2.

> [!solution]- Решение
> На машине, где писался курс, получилось примерно так (у тебя числа будут другими, но порядок тот же):
>
> | | Debug | Release |
> |---|---|---|
> | 10 кадров | ~610 мс | ~39 мс |
> | 1 кадр | ~61 мс | ~3,9 мс |
>
> 1–2. Release быстрее примерно в **15 раз**.
> 3. В Debug один кадр занимает ~61 мс, бюджет 16,7 мс превышен почти в 4 раза: игра шла бы с частотой ~16 FPS. В Release ~3,9 мс, это около четверти бюджета.
> 4. В Release ~10 000 000 частиц за 3,9 мс, то есть ~2,5 млн частиц за 1 мс и **~5 млн** за 2 мс.
>
> **Почему такая разница?** В Debug:
> - каждое обращение `x[i]` — вызов функции с проверкой индекса (отладочная стандартная библиотека);
> - переменные хранятся в памяти, а не в регистрах, после каждой строки;
> - нет **векторизации**: в Release компилятор использует SIMD-инструкции процессора, которые обрабатывают 4–8 чисел за одну инструкцию (подробно в модуле 11).
>
> **Вывод для движков:** производительность **всегда** измеряется только в Release (или RelWithDebInfo). Замеры в Debug ничего не говорят о реальной скорости.

## Задание 6. Под капотом своими руками ⭐⭐⭐

> [!task] Условие
> Повтори эксперименты из [[00.2 Как исходник становится программой]] сам, без CMake, прямо компилятором.
>
> 1. Создай папку `practice/sandbox/` (добавь строку `sandbox/` в `.gitignore`) и в ней файл `pipeline.cpp`:
>    ```cpp
>    #include <print>
>
>    int square(int x) {
>        return x * x;
>    }
>
>    int main() {
>        std::println("7 * 7 = {}", square(7));
>    }
>    ```
> 2. Открой терминал **Developer PowerShell** ([[00.5 Проект курса в VS Code#Шаг 11. Терминал Developer PowerShell|урок 00.5, шаг 11]]) и перейди в папку: `cd sandbox`.
> 3. Выполни по шагам и ответь на вопросы:
>
> | Команда | Что делает | Вопрос |
> |---|---|---|
> | `cl /std:c++latest /EHsc /utf-8 /P pipeline.cpp` | Только препроцессор, результат в `pipeline.i` | Сколько строк в `pipeline.i`? Узнай командой `(Get-Content pipeline.i).Count` |
> | `cl /std:c++latest /EHsc /utf-8 /c pipeline.cpp` | Только компиляция в `pipeline.obj` | Какого размера `.obj`? |
> | `dumpbin /symbols pipeline.obj \| Select-String square` | Таблица символов | Как выглядит декорированное имя `square`? |
> | `link pipeline.obj` | Линковка в `pipeline.exe` | Запусти `.\pipeline.exe` |
> | `dumpbin /dependents pipeline.exe` | Список DLL | От каких DLL зависит программа? Сравни со списком из урока 00.2. Почему он другой? |
> | `cl /std:c++latest /EHsc /utf-8 /O2 /FA /c pipeline.cpp` | Ассемблерный листинг в `pipeline.asm` | Найди в `pipeline.asm` функцию `main` (поиск по `main	PROC`) и число `49`. Есть ли там вызов `square`? |
>
> 4. ⭐ Бонус: переименуй `square` в `square2` только в **определении** функции (вызов оставь `square(7)`). На каком этапе будет ошибка? А если добавить перед `main` объявление `int square(int x);`?

> [!hint]- Подсказка
> Если `cl` «не распознан», ты открыл обычный PowerShell, а не Developer PowerShell. Выбери профиль в выпадающем списке рядом с кнопкой **+** в панели терминала.

> [!solution]- Решение
> 1. В `pipeline.i` около **100 тысяч строк**: всё содержимое `<print>` и заголовков, которые он подключает.
> 2. `.obj` весит сотни килобайт, хотя наш код — пара функций: в него попали экземпляры шаблонов стандартной библиотеки, которые использует `std::println`.
> 3. Строка вида `External | ?square@@YAHH@Z (int __cdecl square(int))`.
> 4. Программа печатает `7 * 7 = 49`.
> 5. В списке, скорее всего, только `KERNEL32.dll`. При ручном вызове `cl` по умолчанию используется **статическая** версия C-рантайма (флаг `/MT`): код CRT и стандартной библиотеки копируется прямо в `.exe`. CMake по умолчанию выбирает **динамическую** (`/MD` для Release, `/MDd` для Debug), поэтому сборка через CMake зависит от `MSVCP140.dll`, `VCRUNTIME140.dll` и других.
> 6. В оптимизированном `main` есть инструкция вида `mov DWORD PTR ..., 49`: компилятор вычислил `square(7)` при компиляции. Вызова `call square` в `main` нет.
>
> **Бонус.** Если вызвать `square` без объявления, будет ошибка **компилятора** `C3861: "square": идентификатор не найден`: компилятор не знает такой функции. Если добавить объявление `int square(int x);`, компилятор успокоится и сгенерирует вызов, но ошибку выдаст **линковщик** (`LNK2019`): определения `square` нигде нет, есть только `square2`.
>
> После эксперимента можно удалить созданные файлы: `Remove-Item pipeline.*  -Exclude pipeline.cpp`.
